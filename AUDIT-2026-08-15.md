## Executive summary — the audit that got tested in production

Yesterday's audit closed with: *"the main risk now is the operational window
between pre- and post-adoption state… that is where prod is most exposed."*
Hours later the first 3B.2 production attempt confirmed it — and the system's
layered defenses held exactly as designed: the forward adoption committed,
the post-commit gate failed, the verified inverse rollback restored the exact
owner/ACL fingerprint, and **zero data was lost or corrupted**. What failed was
everything *around* the mutation: a leftover disposable database, a gate that
could never have run, and a compose/runtime DSN model split. All three root
causes are now fixed and regression-tested in CI; the ~20-minute runtime outage
was recovered the same evening.

Score: **8.5/10** for the codebase (unchanged — it was never the problem);
**process score raised**: the failure modes were caught, understood to root
cause, fixed with tests that provably catch each one, and none of them can
recur silently. Remaining risk is concentrated in one place: the un-executed
half of task #4 (adopt.sh restart-path vs per-role compose DSNs) and the
Gate 11 re-prep that depends on it.

## 2. Architecture — unchanged and now CI-enforced

`eCherha → collector (1 req/60s) → PostgreSQL+TimescaleDB → api → clients`.
The hard invariant (only the server talks to eCherha) is no longer just
documented in AGENTS.md — it is enforced: CI fails on any quoted
`echerha`/`gov.ua` literal in the Android app's production sources (#72).
Verified exhaustively before adding the guard: all 14 client calls go through
`BuildConfig.API_BASE_URL`; no other HTTP client, `URL()`, or hard-coded host
exists in `android/app/src/main`.

## 3. Backend (Python) — clean

- 4,016 LOC / 24 modules; **186 tests** (~1.1:1 test:code); ruff clean.
- Zero injection surface: parameterised SQL everywhere; the single f-string SQL
  (`notifier._mark_sent`) interpolates a two-constant ternary, not input.
- No `eval`/`exec`/`pickle`/`yaml.load`/`shell=True` anywhere.
- Auth: 256-bit device secret, SHA-256 digest only in DB, `hmac.compare_digest`.
- Resource bounds (#16): 16 KB body cap middleware, expensive-endpoint
  concurrency guard, statement timeout.
- Telemetry `completeness_percent` now counts **successful** cycles
  (`error IS NULL`), not attempts — 60 failing cycles/hour used to read as 100%
  completeness during a total collection outage (#63; the dashboard's `<90 →
  WARN` rule now fires as intended).

## 4. Android — adequate; toolchain migration now has a plan and a forcing function

- 3,727 LOC main / **145 tests**; minimal permissions (INTERNET,
  POST_NOTIFICATIONS), `allowBackup=false`, FCM service not exported.
- `compileSdk/targetSdk = 35`; API 36 (#18) still open — but a draft (#52)
  exists and Dependabot empirically mapped the entire migration surface:
  AGP 8→9 removes the need for (and forbids) `org.jetbrains.kotlin.android`;
  Kotlin 2.0→2.4 (semver-minor!) hard-errors on `jvmTarget: String` → needs
  the `compilerOptions` DSL; Gradle 8→9 rides along. Kotlin/ktor/AGP/Gradle
  move as one unit — Dependabot version bumps for gradle/android are parked
  (`open-pull-requests-limit: 0`, #73) until that lands, security updates still
  flow.

## 5. DB — 10 migrations, healthy runtime

- `001`–`009` applied on prod; `010_postgresql_least_privilege.sql` written,
  deliberately **not** stamped (3B.2 applies its ACL; stamping is 3D).
- TimescaleDB on prod: 4 jobs, all `Success`, 0 total failures (cagg refresh:
  193 runs); 3 hypertables / 1 continuous aggregate / 51 MB.
- Cluster is clean again: exactly `avelren, postgres, template0, template1`.

## 6. Deploy / DR — heavier than the app, and that is why prod survived

- Backup: hourly-class timer → gzip dump → **crypt-typed rclone remote**
  (enforced, not assumed) → integrity sidecar + remote digest verify +
  retention. Last run success.
- Restore: disposable-only public CLI; production restore behind a separate
  orchestrator; post-#56 isolation guards (non-prod compose project mandatory,
  `--no-deps` everywhere) — proven twice this week by real isolated
  restore-verifies on the prod host with byte-identical container identity
  before/after.
- Adoption (Decision B): manifest capture → allowlist (now with the
  unexpected-database refusal) → forward/inverse plan builders (identity
  scoped, validation checked) → in-window drift check → committed forward →
  privilege gate (now actually runnable) → verified inverse rollback on any
  post-commit failure. The rollback path is the one piece of this machine that
  has now been exercised **in production** — and it restored the exact
  fingerprint.

## Verdict

Yesterday: "production-ready by architecture, not production-complete by
rollout". Today the sharper version: **the rollback machinery is now
battle-tested in production; the only unfinished engineering is making the
runtime survive that rollback without an operator**. Close F1+F2 (one PR, one

routine window instead of an event. Everything else on the list is normal
backlog, none of it load-bearing for the rollout.
