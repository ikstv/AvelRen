# Інтеграція з єЧергою

Джерело: [єЧерга](https://echerha.gov.ua/). Контракт перенесено з
`AvelRen-ops/INTEGRATION.md`; роботу collector підтверджено журналами й БД
22 вересня 2026 року. Це опис перевіреної інтеграції проєкту, а не гарантія
публічного API або незмінності інтерфейсу з боку джерела.

## Запит і постійна ідентичність

```http
GET https://back.echerha.gov.ua/api/v5/workload/1
Accept: application/json
Content-Type: application/json
X-Client-Locale: uk
X-User-Agent: UABorder/3.9.0 Web/1.1.0 User/guest
X-Device-Id: <persistent-uuid>
X-Device-Name: AvelRen collector
```

Область роботи — вантажівки, `for_vehicle_type: 1`. Автобуси (`/workload/2`)
не включені. Версія API — v5; автоматичного переходу на v4 немає.
Обов'язкові заголовки зберігаємо: за наявним контрактом без них джерело
повертає `403`. UUIDv4 створюється один раз оператором; код його не змінює.
Поточні назви налаштувань: `ECHERHA_BASE_URL`, `ECHERHA_API_VERSION`,
`ECHERHA_CLIENT_VERSION`, `ECHERHA_DEVICE_ID`, `ECHERHA_DEVICE_NAME`.
Реальне значення UUID беремо з чинного налаштування під час погодженого
розгортання, а не генеруємо повторно під час перенесення.

## Частота та помилки

Лише `collector` звертається до єЧерги. Android, браузери, тести й інші
служби не роблять прямих запитів. Для нових клієнтських потреб розширюємо
API AvelRen; прозорий проксі до джерела заборонений.

Між початками циклів — 60 секунд. Не додаємо 60 секунд після завершення
роботи й не запускаємо другий collector паралельно. Заголовок ліміту
`x-ratelimit-limit: 60` не є дозволом збільшувати частоту.

Кожен цикл записується в `collector_runs`, включно з невдалими. Кожне
успішне спостереження зберігається без дедуплікації. На `429`, `5xx` або
timeout записуємо причину та чекаємо наступного циклу, без агресивних
повторів, збільшення паралельності чи обходу обмежень доступу.

## Значення даних

- `wait_time` — секунди.
- `vehicle_in_active_queues_counts` — кількість авто в черзі.
- `entry_eta` — момент вимірювання плюс `wait_time`.
- Прогноз має окрему назву поля й позначення в інтерфейсі.

Під час перевірки джерело повертало 38 черг. Це зафіксований стан,
а не незмінна кількість: приймання змін перевіряє відповідність поточній
відповіді джерела, а не жорстко заданому числу 38.

## Перевірка змін

До зміни перечитуємо цей контракт і відповідний runbook, фіксуємо версію
коду, образів та активні налаштування без значень секретів. Тести працюють
із фікстурами та підміною HTTP, без додаткових запитів до єЧерги.
Після окремо погодженого розгортання перевіряємо запис нових циклів у БД,
частоту, свіжість API та відсутність циклічних перезапусків. Сама відповідь
`200` від API AvelRen не доводить справність запису спостережень.
