# Full audit of the AvelRen project

**Date:** 12 August 2026
**Scope:** backend (Python/FastAPI, ~3,500 lines), Android app (Kotlin, ~2,500 lines), PostgreSQL/TimescaleDB (10 migrations), deploy infrastructure (Docker Compose, Caddy, systemd, ~5,900 lines of bash), tests (~4,400 lines), CI.
**Method:** five parallel lines of analysis (backend, security, DB/deploy, tests/CI, Android) followed by manual verification of key findings against the code. Only confirmed findings with real references to files and lines made it into the report.

---

## 1. Overall assessment

For a project of this size the codebase is extraordinarily disciplined. You can see a culture shaped by a series of internal audits (AUTH-1, SEC-1, A-01/A-02, API-1/3, OBS-1/2, R-04..R-06): fixes are not merely applied but locked in with regression tests and contract checks in CI. Modules map cleanly onto processes (collector, notifier, watchdog, API), invariants are pinned at the DB level (partial unique indexes, cancel-outbox in the same transaction), and migrations are fail-closed with sha256 verification and physical schema verification. No SQL injection, authentication bypass, or secret leak was found.

The weak spots are concentrated not in the design but in the details of resilience under load and in the operational plane: blocking calls inside async loops, one transaction spanning the whole FCM send cycle, a rate limiter that leaks memory, a promised-but-unimplemented retention, an RPO of ~24 hours for data the project itself calls unrecoverable, and a hardcoded allowlist in the restore engine that will break restore after the very first new migration. A separate systemic problem is the inversion of complexity: the bash deploy layer is 1.7× larger than the entire application.

**Final finding counts:** 0 critical, 4 high, 16 medium, ~20 low.

> **Note on false positives.** During the audit three "critical" CI findings (supposedly missing `deploy/postgres-adoption-integration-test.sh`, `AlertReconciliation.kt`, gradle wrapper) turned out to be artifacts of file transfer into the analysis environment — all of these files exist in the repository. They are excluded. The contents of `android/.../res/` were not analyzed (not transferred), so the Android resource part is assessed only via references from code.

## 2. Strengths

**Fail-closed schema management** (`app/src/avelren/migrate.py`, `schema_verify.py`). Contiguous-prefix verification of the migration history, sha256 of applied files, a physical schema contract (including partial-index predicates) before and after application, refusal to auto-baseline after a restore. This reliably catches the classic "restore lost an index" bug.

**Device authentication model** (`subscriptions_api.py:41–106`). Random 256-bit secrets, only a SHA-256 digest in the DB, comparison via `hmac.compare_digest` (timing-attack resistant), the secret returned exactly once, a uniform 401 with no existence oracle, `last_seen` updated only after successful authentication. The "SHA-256 instead of bcrypt" tradeoff is explicitly documented and justified.

**Least privilege in PostgreSQL** (`db/migrations/010_*.sql`, `db/security/bootstrap.sql`). Seven separate roles with column-level grants (notifier can update only `fcm_token`, API only `status, acknowledged_at` in alerts), `PUBLIC` revoked, passwords via `\getenv` + `format(%L)`, a separate DSN per compose service with a contract isolation test in CI. Exemplary.

**Trusted-proxy contract** (`deploy/Caddyfile`, `ratelimit.py:24–36`). Caddy strips client `X-Forwarded-For`/`X-AvelRen-Client-IP` and sets its own header from the socket peer; the limiter trusts only that and validates via `ipaddress.ip_address()`. The contract is locked in with a CI test.

**Backups with real verification** (`deploy/backup.sh`). `umask 077`, size check, `gzip -t`, re-download of the artifact from remote storage and a byte-for-byte SHA-256 comparison, rotation protection against deleting a just-created artifact, dump under a read-only role.

**Notification lifecycle.** Expiring alerts and queuing cancels happen in a single CTE transaction; retry idempotency via `collapse_key`+`ttl`; `/active-alerts` for client reconciliation; `rearm_factor` hysteresis against "flapping" of threshold alerts. On the Android side — a fail-safe reconciler (it clears nothing if the canonical state cannot be obtained).

**Backend test culture.** Tests against a real disposable TimescaleDB, mocks only at the genuine external boundary (FCM/httpx), a fail-closed guard against running on the production DB (`conftest.py:54–73`), a 988-line contract suite for DB privileges, a "expire during push" race test via a second connection.

## 3. High-severity findings

### H-1. A hardcoded relation allowlist will break production-restore after any new migration
`deploy/restore-engine.lib.sh:57–77` (and a duplicate at :156–177) — verified.

The restore engine contains a literal `VALUES` list of exactly 20 relations (14 tables + 6 sequences) and fails with `restore application relation allowlist mismatch` on any extra or missing relation. The moment migration 011 adds a table, every subsequent backup will contain a relation outside the list — and production-restore will **abort in the middle of disaster recovery, after the old DB has already been destroyed** (`dropdb` at :251–253): the stack is left in maintenance with no database. Nothing (no CI test, no comment in the migrations directory) ties "added a migration" to "update restore-engine.lib.sh".

*Recommendation:* derive the list from a single source of truth (a versioned contract in `schema_verify.py`) or add a CI test that runs the current schema's restore through the engine — so drift fails in CI, not during an outage.

### H-2. RPO ~24 hours for unrecoverable data; no WAL archiving
`deploy/avelren-backup.timer` (`OnCalendar=03:20` + 10-min jitter) — verified.

The only backup mechanism is a daily dump. Meanwhile `db/migrations/001_init.sql:19–21` states plainly: "a gap cannot be recovered later, because the source of history keeps nothing." A disk loss at 03:00 permanently destroys up to ~24 hours of minute-by-minute observations — the system's core asset. `docs/disaster-recovery.md` honestly says RPO/RTO are not ratified, but the gap is real.

*Recommendation:* either more frequent dumps (every 4–6 hours — the DB is small, the role is read-only), or WAL archiving via the same rclone-crypt remote; then record the RPO in the runbook.

### H-3. A single DB transaction spans the entire FCM send cycle
`app/src/avelren/notifier.py:85–134` — verified.

The whole cycle (selection + up to 15 s per `fcm.send` sequentially + `_mark_sent`/`_disable_device`) runs inside a single `async with get_pool().connection()`; the commit happens only on exiting the block. If any later statement fails (a DB failure during `_mark_sent`, a process kill), all `last_sent_at`/`send_count` and `fcm_token = NULL` roll back for pushes that **have in fact already been delivered** — the next cycle resends everything and again hits dead tokens. Additionally: while FCM is slow, the connection hangs idle-in-transaction for minutes.

*Recommendation:* a short transaction for the selection, then commit `_mark_sent`/`_disable_device` per-alert (autocommit connection or one transaction per row).

### H-4 (Android). Thread-unsafe lazy initialization of `EncryptedSharedPreferences`
`android/.../data/DeviceStore.kt:39–52` — verified.

`prefs` is a plain field without `@Volatile` and without synchronization, and on a cold start two threads reach it simultaneously: `AvelRenApp.onCreate` → `installation.start()` on `Dispatchers.IO` and `MainActivity.onCreate` on the main thread. Concurrent creation of `MasterKey`/`EncryptedSharedPreferences` for a single file is a known cause of crashes (`KeyStoreException`) and, on first launch, potential corruption of the keyset with **irreversible loss of the device credentials**.

*Recommendation:* `@Synchronized` initialization or double-checked locking with `@Volatile`, plus a one-time eager warm-up in `Application.onCreate` on a background thread (this also closes M-14 below).

## 4. Medium-severity findings

### Security and resilience

**M-1. Mounting the entire host `/run` into the watchdog container** — `docker-compose.yml:83–85`, verified. The comment says "only for /run/reboot-required", but the whole `/run` is mounted, including `docker.sock` (equivalent to root on the host). Read-only does not prevent `connect()` to the socket; the only barrier is the non-root uid 10001. This is a single-layer defense of exactly the class the project already removed from the API container (SEC-1). *Fix:* mount only `- /run/reboot-required:/host/run/reboot-required:ro`, or expose reboot state via a telemetry snapshot, as already done for the API.

**M-2. No limit on request body size** — `deploy/Caddyfile` (no `request_body max_size`), verified. An unauthenticated `POST /devices` reads the entire body into memory before validation; 30 requests/min/IP of a few hundred MB from a handful of IPs and the API container OOMs. *Fix:* `request_body { max_size 64KB }` in the `/api/*` block of the Caddyfile + a Content-Length check in ASGI middleware.

**M-3. Rate limiting covers only 3 write endpoints; expensive read endpoints are unlimited** — `ratelimit.py` (the `"read"` bucket is defined but applied nowhere), `api.py`. `GET /history` (up to 90 days, 1–48 h — raw series with no row limit), `GET /forecast` (the model), `GET /workload` are unauthenticated and unlimited; the connection pool is only 5. A few dozen IPs in a loop take down the DB with no authentication at all. *Fix:* apply `rate_check(request, "read")` to the public GETs; consider a per-device limit on writes.

**M-4. Memory leak in the rate limiter** — `ratelimit.py:56–61`, verified. Cleanup removes only *empty* deques, but a deque empties only if the same key arrives again after the window. A single request from an IP that never returns leaves an entry forever; after 10k unique IPs (internet scanners) cleanup finds nothing, and `_hits` grows unbounded for the whole life of the process. *Fix:* on cleanup, also evict deques whose newest element is older than the window.

**M-5. Hijacking someone else's FCM token (NEW-AUTH-3) — documented but not mitigated** — `subscriptions_api.py:126–134`. Anyone who knows a victim's FCM token (it leaks into logs/crashes, as the code itself notes) can, with an unauthenticated `POST /devices`, silently detach it — the victim stops receiving queue alerts, which is sensitive given this app's purpose. Plus a race between two concurrent `POST /devices` with the same token gives one of them a 500. *Fix:* a challenge-via-FCM before re-binding; logging/alerting on takeover.

**M-6. The promised retention does not exist** — `subscriptions_api.py:121` ("the old one is left orphaned and will be swept by retention") — there is no `DELETE FROM devices`, scheduled job, or retention policy anywhere in the repository. Every reinstall and every anonymous `POST /devices` is an eternal row; orphans bloat the notifier's joins. Likewise without retention: `collector_runs` (~525k rows/year), `health_alerts`. *Fix:* periodic deletion of orphans (`last_seen < now() - 180 days AND fcm_token IS NULL`) in the watchdog; retention for `collector_runs`.

### Backend correctness

**M-7. The seasonal forecast model buckets by UTC, not by Kyiv time** — `forecast.py:105–106, 155–156`, verified (`EXTRACT(dow/hour FROM bucket)` without `AT TIME ZONE`). The seasonality of border traffic lives in local time; the switch to summer/winter time smears the same local time across different UTC slots within the lookback window — degrading exactly the "Tuesday 09:00" signal the module claims to provide. *Fix:* `EXTRACT(... FROM bucket AT TIME ZONE 'Europe/Kyiv')` in `forecast()` and `evaluate()`.

**M-8. A synchronous OAuth token refresh blocks the event loop** — `fcm.py:110–122`. `credentials.refresh(Request())` is a blocking HTTP call to Google from inside the async `send()`; in the notifier this freezes the cycle (and the reaction to shutdown signals) roughly once an hour. *Fix:* `asyncio.to_thread(...)`.

**M-9. A DB failure gives raw 500s almost everywhere** — `api.py`, `subscriptions_api.py`. Only the auth helper maps `OperationalError` → 503; all public GETs and the bodies of write endpoints after auth return 500, so the client cannot tell "server bug" from "retry later". *Fix:* a global exception handler for `psycopg.OperationalError` → 503 + `Retry-After`.

**M-10. Dead admin tokens are never disabled; a shared `collapse_key` for health alerts** — `watchdog.py:259–280`. Unlike the notifier, `_notify` does not check `dead_token`: an unregistered admin token is retried forever, and if it is the only one, new problems are re-sent every 5 min and recovery is eventually lost. The shared `collapse_key="health"` lets a `db_size` alert push out an undelivered `collector_silent`. *Fix:* NULL out dead tokens as in the notifier; `collapse_key=f"health:{kind}"`.

### DB / deploy / operations

**M-11. Backup encryption is assumed but not verified** — `backup.sh:9`. Encryption exists only if the remote `gdrive-crypt:` is really of type `crypt`; the script does not check this, and an env-override allows silently shipping a plaintext `pg_dump` to Google Drive (gzip is not encryption). *Fix:* a preflight check of the remote's type via `rclone config dump`.

**M-12. A backup failure stays silent for days** — there is no `OnFailure=` in `avelren-backup.service`, the watchdog does not check backup freshness, the telemetry snapshot marks stale only after 36 h and only in the passive admin panel. A stale Google token gets noticed by accident. *Fix:* a `backup_stale` check in the watchdog or an `OnFailure=` unit → `health_alerts`.

**M-13. Production-restore destroys the current database with no pre-restore snapshot** — `restore-engine.lib.sh:251–253` (`dropdb` → `createdb`) with no prior dump of the current state. Combined with H-2, restoring yesterday's backup irreversibly throws away everything collected since 03:20 — even perfectly healthy data. *Fix:* a best-effort `pg_dump` of the current database into the workdir before dropdb.

**M-14. Compose: healthcheck only on db, no resource limits and no log rotation** — `docker-compose.yml`. Caddy starts on a bare `depends_on` against a possibly-dead upstream; a hung-but-alive process is caught only indirectly; json-file logs grow unbounded on the host, where disk is shared with the DB. *Fix:* lightweight healthchecks, `logging: {max-size: 10m, max-file: "3"}`, a mem-limit at least for db/api.

**M-15. Inversion of operational complexity: 5,923 lines of deploy bash vs. 3,511 lines of Python** — verified by counting. The adoption machinery alone (`postgres-ownership.lib.sh` — 1,815 lines / 81 KB, `postgres-adopt.sh` + tests) is ~2,950 lines of untyped shell SQL assembly, structurally forbidden to run in production (an `AVELREN_TEST_DB=1` gate). The intent is security-driven and worthy of respect, but this is the most likely place for the next bug and a huge barrier to future maintenance. *Fix:* finish adoption once and archive the machinery, or port the plan/verify logic to Python (psycopg is already there; typed, tested, five times more compact).

**M-16 (Android). Contract drift of `is_active` for ETA targets** — `subscriptions_api.py:326–342` (no `WHERE is_active` filter), `SubscriptionsSection.kt:56–63` (renders everything), verified. After an ack or after the target is passed, `is_active=false`, but the target hangs forever in "What I'm tracking" with a date in the past, as if tracking were still going. *Fix:* filter on the client (`targets.filter { it.is_active }`) or `WHERE t.is_active` on the server.

## 5. Tests and CI

**Assessment.** The backend tests are strong (a real DB, regressions from past audits, races, the privilege contract). The main gaps are not in the quality of the existing tests but in coverage: the most critical data-collection logic is not covered at all. CI runs the full heavy DR suite on every PR with no caching or filters.

**Coverage gaps (backend):**
- `collector.py` — **zero tests** of the core cycle: R-06 transaction split (observations committed independently of alerts), writing derived errors through a fresh connection, the "DB is down → skip the cycle, don't crash" path. A regression that re-couples the transactions would pass CI silently. This is the most important gap.
- `echerha.py` — **zero tests** (`fetch_workload`: HTTP error, non-200, parse error), even though the `httpx.MockTransport` pattern is already in `test_fcm.py`.
- `watchdog.py` — uncovered: `no_data`, `collector_silent`, `collector_errors`, `db_size`, `reboot_required`, the open/resolve cycle. The watchdog is the only thing that notices a dead collector; a SQL typo there is invisible.
- `forecast.py` — only the empty-DB branches are tested; the forecast itself is never checked against seeded data. A quiet off-by-one in bucketing would produce plausible wrong numbers. Also `test_status_thresholds` is parametrized but does not use its parameters — pseudo-coverage.
- API routes with no tests: `GET /thresholds`, a successful `PUT /devices/token` (the FCM-recovery path the Android retry relies on), `GET /forecast/{id}` and `/quality` (routes), the hourly branch of `/history`.

**Coverage gaps (Android):** the whole notification pipeline — `AvelRenMessagingService` (payload parsing, the `cancel_alert_id` contract the Python tests pin only from their side), `Notifications` (the id output reconciliation depends on), `NotificationReconciler.reconcile`, `DeviceStore`, `FcmTokenSyncWorker`, the whole UI. Renaming a field on the client would pass all existing tests. *Fix:* Robolectric tests for `onMessageReceived` + a shared payload fixture for the Python and Kotlin tests.

**CI (`.github/workflows/ci.yml`):**
- The full DR/adoption integration suite runs sequentially on every PR: no `paths` filters, no `concurrency: cancel-in-progress`, no pip/gradle/docker-layer cache; a 240-min job timeout — a hung docker step burns 4 hours of runner time. *Fix:* fast gates separately, heavy integrations as a separate job (main/nightly or by paths).
- Actions are pinned only by major tag (`@v4`/`@v5`) — supply-chain drift; no mypy/pyright (a fully async codebase!), pip-audit, Dependabot, CodeQL. *Fix:* pin to a SHA, mypy in the fast gate, pip-audit.
- Functional tests run under `avelren_admin`, not under the runtime roles — code that quietly needs an extra privilege is caught only if it happens to be covered by a positive privilege test. The identity check at `backend-test.sh:50–60` checks the default DSN but runs the tests under a different one.
- The notifier-cycle tests depend on global DB state (`sent == ["threshold","cancel"]` across the whole DB) and cannot run in parallel (xdist) — an undocumented limitation; devices created in `test_auth.py` are not cleaned up.
- There is no coverage measurement at all (pytest-cov/Kover) — the gaps above are invisible to the team.

## 6. Low severity (briefly)

**Backend:** the `"read"` bucket is dead code (`ratelimit.py:20`); `insert_observations` returns `len(items)`, not the rows actually inserted — `rows_written` may overstate the very number the watchdog trusts (`db.py:88–105`); an O(targets×items) scan in `eta.py:58`; MAE 0.0 is reported as `null` (`forecast.py:177` — a falsy check); `SELECT count(*) FROM observations` — a full hypertable scan on every admin-telemetry request (`telemetry.py:87`); f-string SQL in `cancels.py:60–70` and `notifier.py:61–72` — safe today, but it breaks the uniformity of parametrization; `pip install` with no lock file and no HEALTHCHECK in the Dockerfile — non-reproducible builds contradict the rest of the project's culture; duplication of the threshold/ETA pipelines (`alerts._fire` ≈ `eta._fire`, paired cancel-CTEs) — a doubled surface for maintaining the A-02 invariants; `/health` serves data freshness without authentication.

**DB/deploy:** a redundant index `collector_runs_time_idx` on top of the PK (`001_init.sql:36–46`); `alerts.threshold` without the CHECK that `subscriptions` has (`004_alerts.sql`); `migrate` with no advisory lock — concurrent runs give false deploy failures; `avelren_admin` is a permanent password SUPERUSER with no `CONNECTION LIMIT`; a backup-rotation edge case (a Sunday on the 1st of the month eats the weekly).

**Android:** thresholds are hardcoded instead of `GET /thresholds` (`AvelRenScreen.kt:52`); the release build has no signing config, no minification, an empty `proguard-rules.pro` (enabling minify later will immediately break without keep-rules for Ktor/serialization); `security-crypto 1.1.0-alpha06` — an alpha of a stale library on the secret-storage path (compounds H-4); the build stack is a late-2024 snapshot (compileSdk 35, AGP 8.7.3, Ktor 3.0.2) — an upgrade plan to targetSdk 36 is needed before the Google Play deadline (~31.08.2026); silent failures of subscription loading (`runCatching{...}.getOrDefault(emptyList())` — the card just disappears, the user recreates targets); registration is impossible without an FCM token, even though the backend specifically allows `fcm_token=null` with later delivery via `PUT /devices/token` — a device with no Google Play Services hangs forever in "Connecting…"; `EncryptedSharedPreferences` I/O on the main thread (a jank/ANR window on weak devices); an unknown alert type will be shown and immediately cleared by reconciliation; the `note` text does not disappear, raw English error messages in a Ukrainian-language UI; a past time in `EtaTargetDialog` is validated only by the server.
