## Операція 1 — міграції, окремий GO

З наявного image кандидата одноразово виконати штатний `avelren.migrate`
з каталогом `/release-migrations`, DSN ролі `avelren_migrator` і мережею
чинного Compose. Застосувати **саме 010, 011, 012, 013**; існуючі файли
001–009 не змінювати. Не запускати service `migrate` з production Compose
і не знімати його pin. Після команди перевірити журнал, SHA-256, фізичну
схему та повний pg_dump backup-роллю. Якщо перевірка не пройде — зупинити
наступні операції, зберегти журнали та не стартувати новий API.

010 додає доступні ролям об'єктні права, 011 створює Admin approval і
унікальність адміністратора, 012 — фіксовану функцію 90 днів, 013 —
24-годинний строк блокування чужої інсталяції. Міграції не видаляють
пристроїв. Старі служби працюють через чинний legacy DSN до погодженої
заміни; під час міграцій можливі короткі блокування таблиць.

## Операція 2 — API і notifier, окремий GO

Файл `/var/lib/avelren-release-check-20260924/deploy-013.yml` на сервері
змінює image та DSN лише для API і notifier. Застосувати поверх **обох**
чинних Compose файлів та `.env`. Викликати тільки `up -d --no-deps --no-build`
для `api notifier`; успадкований `build` у config лишається, тому
`--no-build` обов'язковий. Не використовувати `latest` або `compose up`
без переліку сервісів. Звірка `docker compose config` довела, що інші
чотири сервіси лишаються конфігураційно однаковими.

Після заміни перевірити `/api/health`, поточність observations, 24 точки
`/api/forecast/17`, `/api/admin/access` із коректною авторизацією,
нові image IDs, стан notifier і незмінні StartedAt collector/watchdog.
Не надсилати тестові push масово. Якщо API/notifier не працюють —
`rollback-013.yml` із root-only каталогу повертає перевірений baseline
  image та чинний legacy DSN лише для цих двох сервісів. Міграції 010–013
  залишаються застосованими; baseline API вже запущено проти ізольованої
  схеми 013, health/checkpoints/workload повернули 200.

## Окремі наступні операції

- Підтвердити саме поточну інсталяцію власника, PIN вводити без показу в
  чат, аргументах команди, Git чи логах. Після входу перевірити, що Admin
  рівно один і щоденний звіт адресовано саме поточному токену.
- На notifier виконати dry-run retention, звірити кількість. Після окремого
  GO — одноразовий apply і systemd timer 04:00 UTC. Видалення незворотне
  звичайним rollback образу; restore БД — окрема погоджена операція.
- Після підтвердження роботи очищення оновити живу сторінку `/privacy`.
  Перед заміною зберегти початковий HTML, перевірити host/container SHA
  і реальну HTTP-відповідь; bind mount може утримувати старий inode.
- Після серверного приймання завершити Android меню, повний телефонний
  сценарій і фінальний GitHub/Play реліз 0.1.1.
