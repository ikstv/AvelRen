# План поступового перенесення

## Мета

Зробити `AvelRen-ORIGINAL` єдиним приватним робочим репозиторієм AvelRen зі зрозумілою структурою, українською документацією та перевірками відповідних компонентів.

## Поточний етап

Перший блок collector/notifier, спільні модулі й маніфест походження
перенесені до `services/backend/`. PR #2 із ядром і міграціями злитий у
`main` (merge commit `9dddad1403fcddabb01c5d3a4ed72e617538851f`); його
перевірки core та database пройшли. На production застосовані лише міграції
001–009 і їхні хеші збігаються з маніфестом; 010 та 011 не застосовані.

У наявному PR #3 зібрані [API та Admin](API-TRANSFER.md),
[watchdog і телеметрія](WATCHDOG-TRANSFER.md) та
[виправлення щоденного звіту](DAILY-REPORT.md). Його основу перемкнуто на
`main`; для синхронізації злитого PR #2 гілка має містити merge-коміт і
повторно пройти перевірки. Кандидати API та watchdog відрізняються від
останнього задокументованого production стану. До злиття PR #3 потрібно
звірити код і тести, особливо щоденний звіт та відсутність миттєвих FCM
сповіщень про інциденти. Датовані докази й контрольні суми — у
[аудиті production](PRODUCTION-AUDIT.md) і
[переліку перенесення](SERVER-TRANSFER.md).

PR #4 Android і PR #1 ops уже існують як наступні гілки; нові дублікати
не створювати. Повна збірка та окреме погодження будь-якого розгортання
залишаються попереду. Публікація Android-версії в Google Play не входить
до цього етапу.

## Послідовність

Пофайлова підготовка серверного етапу: [джерела, рішення та контрольні суми](SERVER-TRANSFER.md).

1. Оформити About, README та початкові правила роботи.
2. Звірити обидва джерела й унікальні локальні зміни. Скласти перелік актуальних гілок, тегів, PR та відкритих питань із посиланнями на оригінали.
3. Погодити структуру за фактичними залежностями коду й спосіб збереження історії. Зафіксувати вихідні коміти для перенесення.
4. Переносити компоненти окремими завершеними змінами; для кожного додавати потрібні перевірки та інструкції.
5. Перевірити взаємодію застосунку й API, міграції, резервування та відновлення на тестовому середовищі.
6. Після окремого погодження перевести робочі процеси на новий репозиторій.
7. Після стабільної роботи вирішити долю старих репозиторіїв і перейменування `AvelRen-ORIGINAL` на `AvelRen`.

## Орієнтовна структура

`services/backend/` і `db/` уже створено. Android та повні експлуатаційні
сценарії переносимо окремими блоками; межі уточнюємо з урахуванням спільних
модулів і збірки Docker. Production-збірка ще попереду.

```text
apps/android/       Android-застосунок
services/           Серверний код і спільні серверні модулі
db/                 Міграції та контракти бази даних
ops/                Експлуатаційні сценарії й документація
docs/               Архітектура, розробка та рішення
.github/workflows/  Автоматичні перевірки
```

## Принципи перевірок

| Зміна | Очікувані перевірки |
| :--- | :--- |
| Лише документація | Посилання, формат і захист від випадкового додавання секретів |
| Android | Збірка, аналіз коду та відповідні тести застосунку |
| Серверний код | Серверні тести й потрібні інтеграційні перевірки |
| База даних | Міграції, права доступу та залежні серверні сценарії |
| Експлуатаційні сценарії | Перевірки змінених сценаріїв і їхніх залежностей |
| Спільні конфігурації або самі workflow | Усі набори, на які впливає зміна |

Фільтри мають враховувати залежності, а обов'язкові статуси GitHub — коректно завершуватися навіть для пропущених наборів. Регулярний повний прогін допоможе виявляти помилки взаємодії компонентів. Скорочення очікування не означає вилучення потрібних тестів.

## Що зберігаємо

- Перевірений код, незмінні застосовані міграції та правила роботи з даними.
- Походження зображень і шрифтів, ліцензійні повідомлення.
- Історію рішень і зв'язок актуальних питань з оригінальними issues та PR.
- Унікальні локальні зміни до їх окремого розбору.
- Старі репозиторії до підтвердженого завершення переходу.

Гілки, теги та відкриті питання оцінюємо за змістом. Закриття, видалення й зміни робочого сервера виконуються окремо від оформлення нового репозиторію.


## Захист основної гілки та обов’язковий CI

Перевірка GitHub від 23 вересня 2026 року показала, що приватний репозиторій не має активного захисту для `main` (`protected: false`). GitHub повертає вимогу плану вище Free для branch protection/rulesets приватного репозиторію; [документація GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) підтверджує доступність захищених гілок у приватних репозиторіях для Pro, Team та Enterprise.

На перевіреному commit PR #2 успішно завершилися статуси `core` і `database`. Поточні workflow мають фільтри шляхів, тому ці статуси можуть не запускатися для змін інших компонентів. Не встановлювати їх як універсально обов’язкові: пропущені перевірки можуть заблокувати PR. Перед увімкненням захисту потрібен стабільний обов’язковий CI-gate, який запускається для кожного PR і вимагає лише перевірки, відповідні зміненим компонентам.

Під час аудиту план або видимість репозиторію не змінювали; production не зачіпали. До появи доступного плану та стабільного CI-gate захист `main` лишається невирішеним пунктом переходу.


## Доступ до резервних копій секретів — 23 вересня 2026 року

Канонічна точка входу — [SECRETS-RECOVERY.md](SECRETS-RECOVERY.md).
У `main` додано `AGENTS.md`, інструкцію, публічний сертифікат Android,
публічний host key сервера і [Get-ProjectSecret.ps1](../tools/Get-ProjectSecret.ps1).
Причина: попередні інструкції існували лише в гілці PR #2; інший агент,
який відкривав `main`, їх не бачив. Документацію доступу синхронізовано
з PR #2 без перенесення серверного коду в `main` у цьому кроці.

Власник завершив вхід GitHub CLI як `ikstv`; токен у системному `keyring`.
Helper перевіряє ID/приватність репозиторію, draft release, SHA-256 та
права локального каталогу поза Git. Шість комплектів: `android`,
`certificate`, `server`, `ssh`, `ssh-laptop`, `keepass`.

Завантажено й звірено 9 файлів комплектів та старий знімок інструкції.
Android-приватний ключ успішно відкрито паролями з GitHub; сертифікат
збігається. Серверний архів містить п'ять читабельних конфігурацій,
зокрема Firebase service account, паролі БД та rclone crypt recovery.
Архів і Android properties незашифровані, захищені доступом до приватного
Release; актуальність значень щодо production цією перевіркою не доведена.

Знайдену на ПК резервну SSH-пару додано до приватного draft release.
Після окремого `go` власника public key
`SHA256:uGE19uDEANDxIIdHevENqBV/af+xwrVF7nGPvJAaews` додано до
`averlenadmin/.ssh/authorized_keys`. Оригінал збережено; контрольні суми
й порядок відкату наведено в інструкції. Підтверджено вхід завантаженою
з GitHub копією без ssh-agent і збереження старого входу. Сервіси,
застосовані міграції, права БД і конфігурацію застосунку не змінювали.

KeePassXC перевірив KDBX без password component і з порожнім паролем:
обидва способи відхилено з помилкою HMAC. Релевантні папки, ревізії,
коментарі Drive й стандартні локальні місця не дали фактора розблокування.
У Drive AvelRenBackups 25 декодованих імен означають 13 SQL-дампів і
12 контрольних сум; вміст дампів не читали. Дублювання поточних Android,
server і ssh комплектів на Drive ще слід підтвердити. Це не блокує
їх отримання з GitHub.

Перевірки: синтаксис helper у PowerShell 5.1 і 7; реальне завантаження,
SHA-256; Android KeyStore; структура серверного архіву; SSH-вхід;
посилання документації. Відсутність CI не означає успішний CI.
Важкі серверні тести вручну не запускали.

Попередні операції із Drive в цьому завданні: прочитано копію KDBX;
за прямим дозволом власника назавжди видалено Google Doc
`[alerts.in.ua] API токен` (23 вересня 2026 року). Коди GitHub recovery
не читали й не змінювали.
