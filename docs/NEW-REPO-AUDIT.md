# Аудит нового приватного репозиторію

Перевірена база: `c0e53ee`, 2026-09-22. Це аудит коду й конфігурації
`AvelRen-ORIGINAL`, не повторний огляд production або Google Drive.
Результат: перевірені компоненти збираються, але репозиторій **ще не готовий
до повного production-переходу або релізу без додаткових робіт**.

## Пріоритетні знахідки

| Пріоритет | Знахідка | Стан |
| --- | --- | --- |
| До релізу | OnboardingScreen обіцяє автоматичне видалення даних через 90 днів, а механізм retention пристроїв не перенесено. Текст і серверна поведінка мають збігатися. | Блокер R09; не доводить відсутність усіх зовнішніх механізмів на production, який тут не перевірявся |
| До релізу | MainActivity може обрати FLEXIBLE update, але в перенесеному коді немає обробки DOWNLOADED / completeUpdate. Завантаження не дорівнює встановленню. | Блокер R07; потрібне окреме виправлення і Play-тест |
| До rollout R02 | Вікно maintenance читається API та кешується Android, але автоматичний reboot ще не публікує його. | Чесно обмежено в SERVER-STATUS.md; не оголошувати це автоматизацією production |
| До переходу | Не перенесені повна production-збірка, backup/restore та release_notice; публікацію APK і стан підпису не перевірено. | Наступні блоки, не загублені файли |
| Виправлено після аудиту | Шаблон `docs/*PROVENANCE.json` у трьох серверних workflow захоплював Android-маніфест. | Замінено явними серверними маніфестами; додано регресійні приклади вибору CI |
| Виправлено після аудиту | Android CI не реагував на зміну серверного API-контракту. | Додано конкретні API-модулі, не всю серверну папку |
| Виправлено після аудиту | Майбутня доставка змін на телефон не мала єдиного реєстру доказів. | RELEASE-READINESS.md та обов'язкове правило в AGENTS.md |

Контракт FLEXIBLE update підтверджено за [Android Developers](https://developer.android.com/guide/playcore/in-app-updates/kotlin-java#flexible_update):
завершення встановлення має бути окремо оброблене застосунком.
Перенесені функції не виправляємо довільним великим рефакторингом під час аудиту.

## Що перевірено

- Чотири серверні маніфести та Android-маніфест: 117 вихідних записів.
  Початкові SHA збережені; п'ять явно описаних редакцій мають revision.
  Імпорт Android виконаний із Git blobs main, не з брудної робочої папки.
- Збережені 11 міграцій; змін застосованих SQL-файлів у цьому етапі немає.
- Колектор і контракт єЧерги не змінено; новий `/status` не звертається
  ні до первинного джерела, ні до БД.
- Локально 181 Python unit-тест, 113 JVM-тестів та Android-компіляція успішні.
  CI бази c0e53ee: core 37 с, database 2 хв 37 с, watchdog 2 хв 5 с,
  API 3 хв 55 с, Android 4 хв 19 с; усі успішні й працювали паралельно.
- Проста перевірка локальних Markdown-посилань у 18 документах бази не
  знайшла відсутніх файлів. Це не перевірка всіх зовнішніх URL та anchor.
- У поточних відстежуваних файлах пошук приватних PEM-ключів, типових
  GitHub-токенів та AWS access-key ID не дав збігів. Це обмежена перевірка,
  не повний аудит секретів, Git-історії чи вкладень релізів.
- Кеші, build, keystore і локальні конфігурації не перенесені в Git.
  Походження фото, шрифтів і wrapper зазначено в ASSETS.md.
  OFL-ліцензія збережена побайтово, включно з початковим кінцевим пробілом;
  повний diff --check через це має одне успадковане зауваження.

## Розділення перевірок

| Зміна окремого майбутнього PR | Набори |
| --- | --- |
| Android UI або ANDROID-PROVENANCE | Android; короткі правила репозиторію, коли змінено маніфест |
| Watchdog, collector та інші внутрішні серверні модулі | Серверні; без Android |
| Публічний API-контракт | Серверні та Android |
| Лише документація | Коротка перевірка правил і походження, без збірок |

`verify_ci_scopes.py` читає YAML і перевіряє 14 прикладів для PR/push.
Це перевірка заданих glob-прикладів, не повна емуляція GitHub Actions.
Серверні набори поки спільно реагують на backend через спільні залежності.

У накопичувальному PR #1 GitHub порівнює всю гілку з main, тому присутність
обох імпортів запускає обидві групи навіть після документального коміту.
Це не залежність Android-збірки від серверної. Для коротких наступних PR
потрібно завершити цей етап; необмежено накопичувати весь майбутній проєкт
в одному відкритому PR і водночас очікувати лише тести останнього коміту
не відповідає роботі стандартних path filters.

Gradle-кеш тепер може записуватися з нашого PR, а для fork лишається
read-only. Наступні запуски цього PR зможуть його використати; це не
обіцянка фіксованої тривалості. [Поведінка кешу Gradle](https://github.com/gradle/actions/blob/main/docs/setup-gradle.md#using-the-cache-read-only).

## Чого цей аудит не доводить

Не виконані візуальні й мережеві сценарії на реальному телефоні, доставка
FCM, Play Update end-to-end, restore резервної копії та перевірка нової
збірки на production. Повний vulnerability-аудит залежностей, lint та
регулярний повний CI також не завершені. Старі PR та гілки не видалені,
правила GitHub не оголошені налаштованими лише через зелені тести.
Усі приймальні кроки — у [реєстрі релізу](RELEASE-READINESS.md).
