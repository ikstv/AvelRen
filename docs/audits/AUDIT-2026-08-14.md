# AvelRen — Full Project Audit (2026-08-14)

Read-only analysis of the whole tree at `main` @ `d5878e6`. No files modified
during the audit. Supersedes the operational parts of `AUDIT-CONSOLIDATED-2026-08-12.md`.

## Executive summary — healthy project, mature process

Small, disciplined, well-tested codebase; security is clean; infrastructure is
heavier than the app itself (deliberately — DR and least-privilege). The main
incompleteness is the **least-privilege rollout on prod** (in progress, 3B.1
done). Overall: ~8.5/10 for a pre-1.0 service; release blockers largely closed.

## 1. Architecture — clean, with a hard invariant
`echerha → collector (1 req/60s) → PostgreSQL+TimescaleDB → api → clients`.
Only the server talks to eCherha; clients read only our API. Collector and API
are one image, two commands.

## 2. Backend (Python) — 4000 LOC / 24 modules, ~1:1 tests
- Parameterised SQL everywhere — zero injection surface.
- Zero bare-except / swallowed errors.
- Fail-closed migrate (A-07), schema_verify cross-checks physical schema vs history.
- 4 `noqa/type:ignore` in the whole codebase.

## 3. Security — strongest area
- Device auth timing-safe: `hmac.compare_digest`, SHA-256 of a 256-bit secret; DB stores only the hash.
- Zero hardcoded secrets; passwords only via env/`.env` (600).
- Trusted-proxy rate-limit; client IP never persisted.
- Least-privilege 7-role model (migration 010, column-scoped `devices` access); rollout in progress.
- Documented residual risk NEW-AUTH-3 (FCM-token transfer) — honest, not account-takeover.

## 4. Infra / DB / DevOps — heavy but proven
- 8714 LOC shell (adoption/restore/backup/ownership), CI-covered (contract + integration).
- Backup: encrypted off-host, `umask 077`, trap-cleanup, crypt-only gate; restore proven live (346k rows, 2026-08-14).
- Adoption: forward/inverse plan, drift-check, evidence stages.

## 5. Tests / CI — solid
- Backend 4400 LOC (19 files) + Android 29 kt (9 test files); test:code ~1:1.
- CI: 3 jobs (completeness / backend-tests / android-build), push[main]+PR, green.

## 6. Android — adequate, separate track
29 kt, 9 tests. API 36 migration (#18) not started.

## 7. Docs — 8 runbooks
privacy-and-retention, disaster-recovery, backup-key-escrow, restore, trusted-proxy, adoption-runbook, backend-testing, forecast.

## 8. Prod state — rollout in progress
3A done · 3B.1 done (7 roles on prod) · 3B.2–3F pending. Prod still single-role `avelren` SUPERUSER owns the data; migrations at 009.

## Findings (new, by priority)

| ID | Area | Finding | Priority |
|---|---|---|---|
| **F1** | DR | Restore engine hard-requires `avelren_admin` → pre-adoption single-role DR is not covered by the tooling. **Resolved (docs):** on inspection this is a deliberate, contract-enforced adoption-era guard, not a bug — the engine is a post-adoption tool. Pre-adoption recovery is now a documented manual procedure in `disaster-recovery.md`, without weakening the guard. | resolved |
| **F2** | DR | Timescale hypertable restore needs `timescaledb_pre_restore()`/`post_restore()`; a plain `psql` load without them stalls on chunk FKs. **Resolved (docs):** the engine already calls both (lib:262/242); only the *manual* pre-adoption path needed them spelled out — now in `disaster-recovery.md`. | resolved |
| **F3** | Shell | `telemetry-snapshot.sh` lacks `set -euo pipefail` (standalone script) | low |
| **F4** | Ops | `observations` retention is indefinite (deliberate — no PII, history is the product); now documented in privacy-and-retention.md | info |
| **F5** | Monitoring | No independent external monitor — all checks are in-process; a host death has no outside observer (#22) | medium |

F1/F2 are not blockers but are critical for real DR: if prod fails **before**
adoption completes, the tooling cannot restore it (needs a legacy-admin mode +
timescale-aware flags). Close before 3B.2.

## Verdict
Production-ready by architecture and security; not production-complete by
rollout. The main risk now is the operational window between pre- and
post-adoption state (F1/F2 — DR coverage of the single-role prod). Recommend
closing F1/F2 before 3B.2, because that is where prod is most exposed.
