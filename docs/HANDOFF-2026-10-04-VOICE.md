## Що вже прийнято

Локально на продуктовому механізмі: media0, скасування голосу через
«Зрозуміло», п'ять повних фраз, незмінні WAV після повторного відкриття,
fallback без WAV, ACK до старту та повага до заблокованих каналів.
Справжній FCM: власник почув прогноз Чопа у фоні з media0; повторна доставка
точного дубля підтверджена Android method trace й не запустила голос.

Початковий голос uk-UA-language, pitch1/rate0.88 збережено. Фрази:
«Можливий початок масової реєстрації …» та «Почалось зростання черги …».
Ліміт вибору 5 КПП; порожні вантажівки озвучуються окремо. Слово «наплив»
не повертати. Прогноз експериментальний, точність 99% не доведена.

## Найближчий крок

1. Уточнити чутність другого нового прогнозу Чопа о 12:27:04 Києва:
   технічне завершення є, відповідь власника ще очікується. Не підміняти її PASS.
2. Підготувати новий конкретний FCM-план і отримати дозвіл на відновлення
   того самого QA-клієнта, встановлення, обмежену кількість push та cleanup.
   Попередній повтор завершений cleanup після 3/8; не поновлювати його мовчки.
3. Перевірити справжній FCM фактичного початку, нову спробу після ACK,
   голос із заблокованим екраном для Краківця, Ягодина, порожніх вантажівок
   і Рави-Руської. За першого FAIL/UNKNOWN зупинятися й прибирати QA.
4. Закрити решту погоджених телефонних сценаріїв: overflow/deadline,
   недоступний TTS і lifecycle abort. Автоматичні тести не закривають ці пункти.
5. Звірити весь реєстр релізу. Опис 1.0.3 редагує власник; спочатку GitHub
   Release 1.0.3, потім Google Play. Нічого з цього ще не опубліковано.

Перед кожним push перевіряти фактичну importance/sound URI обох каналів,
WAV/SHA, дозвіл сповіщень, media0/notifications>0, NORMAL/zen OFF і фон.
Xiaomi off/on може лишити канал LOW2: увімкнений перемикач не гарантує звуку.
Для JSON helper явно задавати UTF-8; Windows Python може читати як CP1251.
Дублі та ACK перевіряти з доказом фактичного входу onMessageReceived.
Тестовий застосунок не робить production registration чи серверний ACK.
