# Захист інтервалу HTTP-запитів collector

Під час read-only аудиту 11.10.2026 виявлено, що встановлений collector
містить захист, відсутній у main. Після явного дозволу власника отримано
дві source-копії для порівняння; їхні SHA-256 збіглися з попереднім
спостереженням. Ця ревізія переносить відповідну поведінку без змін
endpoint, Device ID, типу транспорту, міграцій або server configuration.
Походження історичного commit label образу не встановлено; доказом
тотожності source-копій є хеші, а не label.

## Контракт

- Новий poll_loop чекає 60 секунд перед першим циклом, щоб автоматичний
  restart не спричиняв негайний повторний запит.
- Наступний цикл відраховується від фактичного старту. Запізнення не
  компенсується скороченням наступного інтервалу до 55 секунд.
- Один RequestPacer на послідовний poll_loop перевіряє монотонний час
  прямо перед send, після підготовки запиту і локального запису spool.
  Між спробами щонайменше 60 секунд; раннє пробудження перевіряється ще раз.
  HTTP-помилка також займає інтервал. Це не міжпроцесний distributed lock:
  чинна вимога одного collector залишається обов’язковою.
- HTTP redirects явно вимкнені навіть для клієнта з follow_redirects=True.
- Діагностика non-200 містить лише валідований hex/UUID request/correlation ID
  і числовий Retry-After до шести цифр. Дублікати/довільний текст не пишуться.
  Retry-After не запускає повторів і не змінює 60-секундний контракт.
- Очікування pacer не включається в duration_ms HTTP-запиту.

Попередні зміни spool і transport diagnostics збережені:
[spool](../ops/COLLECTOR-SPOOL.md),
[діагностика](SURGE-RECOVERY-DIAGNOSTICS-2026-10-08.md).

## Перевірка та межі

Unit-тести перевіряють стартову паузу й stop у ній, late wakeup,
передавання спільного pacer, 429/503/timeout без скорочення інтервалу,
раннє пробудження, cancellation до send, тривалість запиту, redirects
і фільтрацію діагностики. HTTP — тільки MockTransport; годинник підмінений.
Не виконуються запити до джерела або production DB.

Комбінований тест `poll_loop` із реальним SQLite spool та MockTransport
перевіряє затримку першого `spool.begin` на 15 секунд: цикли починаються
на 60/120/180 секундах, HTTP-спроби — на 75/135/195. При навмисному
вимкненні pacer тест падає через 45-секундний проміжок між спробами.

Daemon acceptance має враховувати стартову паузу кожного нового процесу:
для двох перших циклів потрібно 120 секунд, для трьох після restart — 180,
для одного — 60. Межі очікування становлять відповідно 150/210/90 секунд,
включно з 30-секундним запасом на scheduling і завершення запису spool.
Runtime acceptance також чекає перші два цикли до 150 секунд.
Після відкату він окремо очікує нову HTTP-спробу та її підтверджений replay
до 90 секунд. Порожній pending spool сам по собі не доводить нового циклу:
перевіряється приріст кількості спроб і відповідність `acked_count` усім
зафіксованим спробам, щоб виключити ще незавершений `started` запис.
Це виправляє застарілі очікування тестів; перевірка інтервалів HTTP,
FIFO, відсутності дублікатів і capture-only залишається обов’язковою.

Це перенесення коду та локальні тести, не нове серверне встановлення.
[Реєстр готовності](RELEASE-READINESS.md) розділяє код, CI та deployment.

## Відоме обмеження часу спостереження

Як і в перевіреній серверній версії, timestamp циклу фіксується перед
spool.begin і HTTP-підготовкою. Якщо pacer потім очікує через попередню
затримку, це час початку циклу, а не точний час send. Зміна семантики
цього поля не входить до перенесення; її слід окремо оцінити для ETA.
