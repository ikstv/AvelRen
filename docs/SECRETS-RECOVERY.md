використовувати комплект `ssh` та команду нижче; пароль старого ключа ноутбука
для цього не потрібен.

## Порядок роботи агента

1. Знайти потрібну потребу в таблиці й запустити відповідний комплект.
2. Використати вже авторизований GitHub CLI. Підключення GitHub у застосунку
   та локальний вхід `gh` — різні способи доступу. Помилка одного не означає
   втрату файлів в іншому.
3. Використати шлях, який повернув скрипт. Значення паролів брати локально
   з потрібного файла без друку в чат чи журнал. Не комітити завантаження.
4. Якщо доступ не спрацював, відрізнити відсутню мережу/доступ sandbox,
   неавторизований `gh`, відсутнє вкладення, неправильний SHA-256 та
   помилку розшифрування. Не робити висновку про втрату всіх ключів.
5. Просити власника лише про конкретно відсутню дію чи дані після цих
   перевірок. Для входу GitHub потрібне підтвердження власника у браузері;
   паролі й токени в чат для цього не потрібні.
6. Записати результат і обмеження тут. Отримання резервної копії не є
   дозволом на ротацію, застосування конфігурації чи інший запис на production.

## Один раз на кожному Windows-ПК

Потрібен [GitHub CLI](https://cli.github.com/); для SSH — Windows OpenSSH Client
(команда `ssh`). Для роботи в репозиторії:

```powershell
gh auth login --hostname github.com --git-protocol https --web
gh auth status --hostname github.com
```

Власник вводить одноразовий код на [сторінці входу GitHub](https://github.com/login/device)
і підтверджує акаунт із доступом до цього приватного репозиторію.
На робочому ПК 23 вересня 2026 року перевірено вхід `ikstv` із токеном
у системному сховищі `keyring`. На домашньому ПК цей вхід треба перевірити
окремо. Не використовувати `--show-token` або `--insecure-storage`.

Якщо PowerShell блокує запуск скрипта з довіреної копії репозиторію,
дозволити локальні скрипти лише для поточного сеансу:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned -Force
```

Це не змінює політику комп'ютера чи користувача постійно. Корпоративну
Group Policy не обходити; її заборону фіксувати як конкретне обмеження.

[Скрипт отримання](../tools/Get-ProjectSecret.ps1) перевіряє ID і приватність
репозиторію, конкретний draft release та SHA-256 кожного файла.
Файли потрапляють у новий підкаталог
`%LOCALAPPDATA%\AvelRen\secrets\<комплект>-<ідентифікатор>`
із доступом лише поточного Windows-користувача. Попередні копії не
перезаписуються. Скрипт повертає лише шляхи після перевірки всього комплекту
та не розпаковує серверний архів.

Після перейменування репозиторію використовувати
`-Repository ikstv/AvelRen` **лише коли це стане назвою саме цього
репозиторію з ID 1381378215**; зараз назву `ikstv/AvelRen` має старий
репозиторій. Потім оновити типову назву в скрипті й посилання тут.

Постійні ідентифікатори резервної копії: release ID `393893592`,
pending tag `secure-backup-2026-09`. Браузерний шлях чернетки
`untagged-396e123926d9d8a52944` відрізняється від tag для CLI — це очікувано.
[GitHub CLI підтримує вибір вкладень і каталогу завантаження](https://cli.github.com/manual/gh_release_download).
Не завантажувати весь реліз у корінь Git checkout.

дозволено в `/home/averlenadmin/.ssh/authorized_keys`.

- Резервний ключ: `SHA256:uGE19uDEANDxIIdHevENqBV/af+xwrVF7nGPvJAaews`.
- Ключ ноутбука: `SHA256:MPWIdimchoJ1w+YgGyUcR0zWZSQGrjHntFEVqnwlL5s`.
- ED25519-ключ **самого сервера**: `SHA256:o7IMJxdis/8KUh/AtLzVzRA8rxxQijdC+aZIKlWHOes`.
  Його [публічний запис known_hosts](security/avelren-production-known_hosts)
  отримано через раніше довірений SSH-сеанс.

З кореня свіжої копії цього репозиторію:

```powershell
$ErrorActionPreference = 'Stop'
$secretPaths = @(.\tools\Get-ProjectSecret.ps1 -Name ssh)
$privateKey = $secretPaths | Where-Object { $_ -notlike '*.pub' }
ssh -F none -o IdentityAgent=none -o IdentitiesOnly=yes -o BatchMode=yes `
  -o StrictHostKeyChecking=yes -o HostKeyAlgorithms=ssh-ed25519 `
  -o UserKnownHostsFile=docs/security/avelren-production-known_hosts -i "$privateKey" averlenadmin@204.168.137.84
```

Ключ `ssh` не має passphrase; захищати завантажений файл як пароль.
Не прибирати перевірку host key. Невідповідність відбитка потребує перевірки
причини через довірений канал. Успішно перевірено вхід саме завантаженою
копією з вимкненим ssh-agent; старий вхід `avelren-production` також працює.

Активація додала один public key без перезапусків сервісів.
Початковий файл: `/home/averlenadmin/.ssh/authorized_keys.before-recovery-4907a620532b.bak`,
SHA-256 `4907a620532b2c8417b8cd97656b6f37fb7d0f5d3b04c46810f9464ac446c8e6`.
SHA-256 після додавання: `dedcd3726a62fe703ba311b7d2ea0ca1ceed2c9d3ab3c25e00a220035d93b4b4`.
Відкат — окрема операція за GO: звірити обидва хеші, зберегти робочий
сеанс старого ключа та відновити початкові байти з цієї копії з режимом
`0600` і власником `averlenadmin:averlenadmin`. Якщо поточний файл змінився,
не замінювати його старою копією без розбору нових ключів.

## Серверний архів

Архів `avelren-server-secrets-2026-09-23.tar.gz` містить:

| Шлях в архіві | Для чого потрібен |
| :--- | :--- |
| `opt/avelren/.env` | Параметри сервісів, паролі/DSN ролей БД і постійний Device ID collector |
| `opt/avelren/secrets/firebase-service-account.json` | Облікові дані Firebase service account для серверного FCM |

Усі п'ять файлів прочитано локально без розпакування на диск; перевірено
структуру конфігурацій і наявність обов'язкових полів Firebase JSON без
виводу значень. Архів **не зашифрований**; properties-файл Android також
читається напряму. Їх захищає контроль доступу приватного GitHub Release.
Це не гарантує шифрування на стороні користувача. Зафіксовані файли є
датованими резервними копіями: актуальність щодо production та дійсність
Google credentials цією перевіркою не доведені.

[GitHub recovery codes](https://drive.google.com/file/d/1InHAKR45KRcH_EhJv3jmD04UYRikFM6V/view)

окремо від GitHub, щоб можна було відновити сам вхід до репозиторію.

У релевантних папках, ревізіях і коментарях окремого фактора розблокування
KeePass не знайдено. У `AvelRenBackups` перевірено 25 імен: після декодування

Перевірено також стандартні локальні місця KeePass/KeePassXC і файли
проєкту: відомого key file чи збереженої конфігурації розблокування не знайдено.
Це обмежений пошук, а не доказ відсутності пароля всюди.

Копії нового Android-комплекту, серверного архіву й резервного SSH-ключа
на Drive під час цієї перевірки не підтверджено. Наявність одного KDBX не доводить резервування
всіх поточних ключів на Drive.

## Правила і результат перевірки

- Значення секретів не потрапляють у Git, журнали, issue, PR або чат.
- Реліз лишається **Draft** у приватному репозиторії. За дозволом власника
  до нього додано знайдену резервну SSH-пару. Наявні вкладення не замінювали.
- Перевірено завантаження всіх 9 файлів комплектів та старого знімка
  інструкції, SHA-256 збігаються. Перевірено синтаксис helper у PowerShell
  5.1 і 7 та збереження UTF-8 BOM для українських повідомлень.
- Android KeyStore із GitHub відкрито паролями з GitHub; прочитано приватний
  ключ і перевірено SHA-256 сертифіката. Серверний архів прочитано на рівні
  структури, без застосування до сервера.
- Після окремого GO активовано резервний SSH public key. Вхід завантаженою
  приватною копією без ssh-agent і старий вхід успішні. Збережено резервну
  копію `authorized_keys`; конфігурацію застосунку, БД і сервіси не змінювали.
- KeePass та passphrase старого ключа ноутбука лишаються невідновленими.
  Поточні комплекти Android, сервера та резервний SSH доступні незалежно.
- Канонічна інструкція та helper доступні в `main` і синхронізовані з
  відкритим PR #2. Однойменне вкладення релізу — історичний знімок;
  перед роботою читати цей файл у Git.
