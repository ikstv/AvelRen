# Уточнення щоденного звіту

Зміни після контрольного аудиту `aafcbe5`. Це код нового репозиторію,
не запис про розгортання на production. Collector, інтеграція єЧерги,
міграції, snapshot-сценарій та клієнтські сповіщення черг не змінені.

## Достовірність

- Звіт приймає лише JSON-об'єкт із `collected_at`, що містить часовий пояс.
  Дані старші за 300 секунд або більш ніж на 60 секунд із майбутнього
  не показуються як поточні: звіт повідомляє причину й невідомі показники.
- Відсутній файл, зламаний JSON і JSON іншого типу означають недоступність.
  Неправильна структура розділів не повинна зупиняти цикл звітності.
- Boolean має три стани: «так», «ні», «невідомо». Невідоме не дорівнює «ні».
  Лічильники приймають лише невід'ємні цілі числа, не boolean чи рядки.
- Диск має бути від 0 до 100%, RAM від нуля до загального обсягу.
  Відсутність одного показника не дає «норму», але не приховує відомого
  перевищення іншого. RAM залишається одним вимірюванням, не добовим піком.

## Доставка

Час незмінний: перший успішний цикл після 12:00 за Europe/Kyiv,
цикл раз на 300 секунд. Передчасних чи миттєвих аварійних push немає.
У тілі є дата звіту, у payload додано `report_id=daily:YYYY-MM-DD`.
Тип `health`, заголовок і основні поля сумісні зі старим Android-обробником.
Цей крок не оновлює Android і не додає клієнтську дедуплікацію.

Для щоденного звіту TTL становить 86400 секунд. Постійний
`collapse_key=health:daily` дає новішому звіту замінити старіший, який ще
очікує доставки на той самий токен. Це обмежена черга останнього звіту,
не архів усіх пропущених днів. Після тривалого офлайну або перевстановлення
старий звіт може не надійти; токен нової інсталяції потребує чинної реєстрації.
Поведінка TTL та collapse описана в [документації FCM](https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-lifespan).

Успіх FCM означає прийняття до доставки, не показ на телефоні. Саме так
тепер сформульований журнал. Тимчасова помилка залишає можливість повтору
наступного циклу; підтверджений мертвий токен очищається як раніше.

## Конкурентні цикли

Перед читанням стану й відправкою цикл отримує транзакційне
`pg_try_advisory_xact_lock` з окремим сталим ключем watchdog. Якщо інший
цикл тримає його, поточний пропускає роботу. Блокування автоматично
звільняється після commit/rollback; воно не блокує collector чи весь сервер.
Механізм описаний у [PostgreSQL](https://www.postgresql.org/docs/16/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS).

Захист діє між копіями нового watchdog у тій самій БД. Старий процес,
який не бере цього блокування, ним не захищений: під час deployment
не можна залишати обидві реалізації одночасно.

Вікно збою після прийняття FCM, але перед commit БД, залишається. Після
такого збою можливий повтор з тим самим report_id. Exactly-once не
обіцяємо; для цього потрібен окремий клієнтський протокол. Поля
`recovery_notified_at` та невикликана стара функція recovery не змінені;
історичні записи не доводять факту recovery push.

## Перевірка та походження

Unit-тести охоплюють типи, межі свіжості, невідомі дані, пороги, часовий
пояс і параметри FCM. Ізольовані тести БД перевіряють послідовність,
конкурентні цикли, звільнення блокування після rollback, помилки FCM,
токени й збереження повідомлення про застарілі дані. Реального FCM немає.

У `WATCHDOG-PROVENANCE.json` початковий `sha256` збережений незмінним.
Для watchdog додано `revision.sha256` та посилання на цей опис.
Перевіряльник перевіряє поточний хеш і наявність опису зміни; решта
імпортованих файлів залишаються побайтовими копіями. Оригінал watchdog
доступний в історії нового репозиторію до цього кроку.

Запуск: unit-команда з README та `bash scripts/test_database.sh watchdog`
у Docker. Зелений CI не підтверджує фактичну доставку на телефон і не
замінює окремий дозвіл та перевірки production-розгортання.
