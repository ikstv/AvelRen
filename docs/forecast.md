# Прогноз черги

## Джерело даних і межі

Android просить прогноз у власного API AvelRen. Сервер читає виміри з таблиці
`observations` робочої PostgreSQL/TimescaleDB. Google Drive у поточній схемі є
місцем для зашифрованих резервних копій, а не джерелом прогнозу.

Поточний базовий розрахунок обмежений останніми 12 тижнями, згрупованими за
днем тижня та годиною Києва. Це обмеження захищає API від необмеженого сканування
історії. Отже, якщо в базі є записи старші за 12 тижнів, вони зараз не беруть
участі в прогнозі. Остання серверна звірка підтвердила понад 2,5 млн вимірів,
але не зафіксувала точний часовий діапазон для кожного КПП; не можна стверджувати,
що запитано всю наявну історію.

Модель для кожного дня тижня й години рахує медіану кількості машин, а також
25-й і 75-й процентилі історичних погодинних значень. Це простий статистичний
базис, а не AI-модель і не гарантія. Один погодинний `sample` — агрегат даних за
одну історичну годину, а не одне хвилинне спостереження.

## Перевірка якості

Оцінка похибки використовує обмежене 12-тижневе вікно: останні сім днів залишаються
відкладеною перевіркою, а медіани навчаються тільки на попередніх годинах.
Верхня межа — початок поточної UTC-години, тому незавершений погодинний агрегат
не оцінюється як повний факт.
Спостереження перевірочного тижня більше не беруть участі у власному прогнозі.
Якщо для часових слотів тестового тижня немає історичного аналога, вони не
входять до MAE. Чесність розбиття не означає, що модель уже точна; для висновку
потрібні результати MAE окремо для часу очікування та кількості машин на реальних
даних і порівняння з простим базисом.

## Наступні вимоги до моделі

- Порахувати доступний період і покриття по кожному КПП без винесення сирої
  історії в Android або Drive.
- Порівняти 12-тижневий базис із довшим вікном на послідовних відкладених
  тижнях. Стару історію використовувати лише якщо вона зменшує помилку.
- Не показувати точне число без достатнього покриття відповідного дня/години;
  показувати медіану, типовий розкид і кількість історичних погодинних агрегатів.
- Залишати фактичні виміри й оцінку прогнозу окремими даними та позначеннями.
- Не називати прогноз AI, доки складніша модель не доведе кращу якість на тих
  самих часових перевірках.

## Перевірка на реальних даних (2026-09-24)

Перевірка виконана тільки читанням публічного API, без запитів до секретів БД і
без будь-яких записів на сервер. Джерела: `/api/history/17?hours=2160`,
`/api/history/17?hours=48`, `/api/forecast/17` і `/api/forecast/17/quality`.
КПП 17 — Чоп (Тиса) – Захонь.

90-денний запит повернув 1 125 погодинних агрегатів із 2026-08-06 21:00 UTC
до 2026-09-24 10:00 UTC (6,94 тижня; медіана 60 хвилинних спостережень на
погодинний агрегат; 41 пропущена година в охопленому інтервалі). Поточний статус
API — `preliminary`, бо ще немає восьми тижнів. Річну сезонність перевірити
неможливо; три додаткові КПП для порівняння також починають історію в цьому вікні.
Повторне read-only читання о 11:00 UTC повернуло 1 126 агрегатів до 11:00 UTC;
нову годину ще не включено до наведених вище backtest-метрик.

На спільному наборі з 782 прогнозованих годин для Чопа медіана останніх двох
повторів того самого дня тижня й години дала MAE **86,6 авто**, прогноз за
попереднім таким самим тижнем — **87,3**, а медіана всіх повторів у доступному
12-тижневому вікні — **112,0**. В останніх 14 днях перевірки похибка сезонного
прогнозу різко зросла: MAE кількості машин на горизонті 1–6 годин — **150,6**,
середнє заниження — **150,3 авто**.

На історичних даних перевірено один гібридний рушій: сезонний профіль плюс
поточне відхилення рівня черги від типового для цієї години:

```text
прогноз(t+h) = max(0, сезонна_медіана(день_тижня, година)
                      + ρ^h × (поточний_рівень − сезонна_медіана(поточного_слоту)))
```

Вага ρ вибиралася тільки на ранній частині даних, а останні 14 днів були
відкладені. Для цієї перевірки оптимальна вага в заданому пошуку опинилася на
верхній межі для всіх чотирьох КПП: Чоп — `ρ=0,99`; три інші — `ρ=1,0`. У
відкладених годинах MAE середньої кількості машин за годину склала:

| КПП | 1–6 год: сезонна → гібрид | 7–12 год: сезонна → гібрид | 13–24 год: сезонна → гібрид |
|---|---:|---:|---:|
| Чоп (Тиса) – Захонь | 150,6 → 36,5 | 150,9 → 86,5 | 153,2 → 144,8 |
| Ягодин – Дорогуськ, ≥7,5 т | 126,5 → 19,9 | 128,3 → 44,2 | 131,0 → 68,7 |
| Ягодин – Дорогуськ, порожні ≥7,5 т | 309,2 → 49,9 | 295,7 → 118,1 | 273,4 → 188,1 |
| Краківець – Корчова, ≥7,5 т | 194,9 → 38,0 | 187,7 → 80,0 | 183,8 → 136,5 |

Усі прогнози для тестового дня використовували тільки інформацію, доступну на
момент прогнозу. Вікно 1–6 год дало найбільший виграш. На 13–24 годинах гібрид
також виграв у трьох КПП. Для погодинного максимуму на Чопі прогноз за
попереднім таким самим тижнем був кращим: MAE **96,3** проти **144,6** у гібриду. Отже, один постійний
коефіцієнт
для всіх горизонтів і КПП не підтверджено. До того ж ρ обрано на верхній межі
перевіреного діапазону — це ознака, що залежність від короткострокового тренду
ще треба дослідити, а не готове значення для коду.

Поправка на рівень сама по собі **не довела, що точніше знаходить годину піку**.
У 24-годинному backtest на Чопі влучання в межах однієї години було 54,6% у
сезонного базису й 53,5% у гібриду. У невеликій окремій перевірці повних днів
EWMA-профіль із вагою 0,5 показав 68,8% проти 59,4%, однак ці параметри вибиралися
на тому ж короткому наборі й результат потребує нового відкладеного тесту.
Величину черги й час її піку треба оцінювати окремо. Наявний p25–p75 покрив лише
**23,6%** відкладених фактичних погодинних середніх, тому це типовий історичний
розкид, а не калібрований інтервал прогнозу.

Окремо перевірено простий демпфований тренд: нахил останніх чотирьох
погодинних відхилень від сезонного профілю додавався до рівневої поправки.
На тій самій часовій перевірці він майже не змінив MAE; на Чопі для 13–24 год
MAE було 153,6 проти 153,0 у сезонного базису. Отже, просто продовжувати останній
нахил у майбутнє теж не можна вважати достатньою формулою.
Практична помилка видна й у живій відповіді: 2026-09-24 близько 13:12 за Києвом
API давав на 14:00 оцінку **60 авто** (`samples=6`), хоча вимір о 13:17 вже був
**226 авто**. О 13:22 останній вимір був 224; за попередні три години черга
спадала приблизно на 6,5 авто/год. Це ще не перевірка результату о 14:00, але
чітко показує, що звичайний тижневий профіль не враховує поточний рівень і напрямок
руху черги.

Production `/forecast/17/quality` повернув повідомлення `estimate on the same
data, optimistic`, `mae_hours=8.84` і `mae_vehicles=null`. Це не є незалежною
перевіркою поточної локальної реалізації, яка відділяє останні сім днів; цей
endpoint на production має стару або іншу логіку оцінки. SSH-ключі з перевіреного
сховища були відхилені сервером, тому отримано тільки погодинні агрегати публічного
API та сирі виміри за останні 48 годин. Повну хвилинну історію з БД не читали.

## Рекомендований напрямок

Залишити **один рушій прогнозу**. Усередині нього поєднати сезонний профіль
Київського дня тижня/години з поточним рівнем черги; ваги й згасання поправки
вибирати окремо для 1–6, 7–12 і 13–24 годин на послідовній перевірці. Фіксовану
ρ та просту лінійну екстраполяцію тренду поки не приймати: перша працює нерівно
на дальшому горизонті, друга не покращила holdout. Для часу піку брати максимум
усього погодинного профілю, а похибку часу й кількості машин рахувати окремо.

Не називати p25–p75 довірчим діапазоном, поки його покриття не відкаліброване.
Зовнішній платний AI API для цього не потрібен. Якщо простий гібрид після
довшого backtest програє, безкоштовний наступний кандидат — локальна регресія
градієнтного бустингу LightGBM (MIT) з ознаками: година/день Києва, поточна черга,
зміна за 15/60/180 хвилин, очікування та лаги 1/24/168 годин. Вона тренується й
рахує прогноз на нашому сервері; платної інференс-підписки немає. Для статистичних
базисів є StatsForecast (Apache-2.0; має SeasonalNaive, AutoETS/Holt і AutoARIMA
для порівняння). Вибір
будь-якого кандидата — тільки за rolling-origin перевіркою з однаковим набором
цільових годин, без підглядання в майбутнє. Методологія такого відкладеного
часового тесту описана у [Forecasting: Principles and Practice, time-series
cross-validation](https://otexts.com/fpp3/tscv.html); пакети та ліцензії:
[LightGBM](https://github.com/lightgbm-org/LightGBM) і
[StatsForecast](https://github.com/Nixtla/statsforecast).

**Що ще потрібно до прийняття формули:** повторити тест через щонайменше ще
чотири тижні та кілька різних КПП; мати доступ до хвилинних даних за весь період;
порівняти кандидат із простим «попередній такий самий тиждень»; протестувати
режими зростання й спаду окремо; перевірити покриття нового діапазону. До цього
гібрид із поправкою на поточний рівень — експериментальний, не
production-ready. Нічого на production не змінювалося.

## Повторна перевірка години піку (2026-09-24)

Для відтворюваності додано [скрипт walk-forward перевірки](../tools/forecast_backtest.py).
Він прочитав лише погодинну історію власного публічного API для КПП 17, 1, 29 і
6; upstream та база напряму не опитувались. На попередніх 14 повних днях
підбиралось `ρ` за MAE кількості авто, останні 14 повних днів (10–23 вересня)
залишались holdout. Щодня перевірялись два моменти видачі — 06:00 і 12:00 за
Києвом — і години до кінця дня. Порівняно сезонну медіану, вимір того самого
часу попереднього тижня та гібрид сезонного профілю з поправкою на останній
погодинний рівень. Окремо перевірено оцінку часу піку як моду історичних пікових
годин того самого дня тижня.

| КПП | MAE авто: сезонна / тиждень тому / гібрид | MAE години піку: сезонна / тиждень тому / гібрид | Пік у межах ±1 год: сезонна / тиждень тому / гібрид | Мода попередніх денних піків: MAE / ±1 год |
| --- | ---: | ---: | ---: | ---: |
| 17 Чоп | 158,42 / 95,14 / **92,90** | **1,71** / 2,75 / 2,21 | **82,1%** / 67,9% / 75,0% | 1,57 год / 82,1% |
| 1 Ягодин | 122,68 / 104,33 / **73,87** | 1,25 / 2,00 / **1,18** | 82,1% / 64,3% / **82,1%** | 1,14 год / 71,4% |
| 29 Ягодин, порожні | 276,69 / 413,14 / **142,98** | 5,81 / **4,27** / 6,15 | 15,4% / **50,0%** / 15,4% | 4,85 год / 30,8% |
| 6 Краківець | 189,88 / 203,10 / **128,45** | **2,96** / 3,86 / 3,36 | **57,1%** / 35,7% / 50,0% | 3,18 год / 42,9% |

За кількістю авто гібрид виграв на всіх чотирьох КПП, але підбір щоразу вперся
у верхню межу пошуку `ρ=0,99`. Для часу піку гібрид не виграв у сезонного
профілю на трьох КПП; попередній тиждень значно кращий для КПП 29. Мода минулих
денних піків теж не має сталої переваги: вона допомогла КПП 29, але програла
сезонному часу піку на інших. Є лише 26–28 перевірочних пар на КПП, а два
внутрішньоденні моменти одного дня залежні між собою. Це корисний діагностичний
результат, але замало для вибору формули чи заяви, що точність піку покращено.
**Поки лишаємо окремі сезонні baseline для часу й експериментальний гібрид лише
як кандидата для числа авто; не підміняємо ним production-модель.**
