# Адміністрування

Статус: реалізація для перевірки перед 0.1.1. На робочий сервер і телефон не встановлено; у Google Play не опубліковано.

## Екрани

`Налаштування → Адміністрування` відкриває дві вкладки:

- **Сервер**: порожня область для майбутньої телеметрії.
- **Admin**: стан підтвердження інсталяції, введення PIN, результат входу або час завершення блокування за Києвом.

PIN не перевіряється в Android і не зберігається в стані, який переживає закриття екрана. Помилка мережі не є успішним входом. Старий сервер без нових маршрутів не надає доступу: екран показує недоступність входу.

## Захист

Чотиризначний PIN є слабким секретом і не є самостійним доказом володіння телефоном. Потрібні одночасно:

1. Дійсна пара `device_id` / `device_secret` поточної інсталяції.
2. Окреме підтвердження саме цієї інсталяції оператором через серверний інструмент.
3. Правильний PIN за відсутності активного блокування.

IMEI, назва моделі, IP-адреса, FCM-токен і переданий клієнтом Android ID не використовуються як доказ права адміністратора. Підтвердження інсталяції не переноситься автоматично після перевстановлення.

Після трьох неправильних спроб підтвердженої інсталяції сервер блокує вхід на 24 години. Стан належить власнику, а не запису інсталяції: повторне підтвердження нового запису не скидає його. Інші користувачі не можуть витратити спроби власника. Паралельні спроби серіалізуються блокуванням рядка БД. Невдалі спроби комітяться, а правильний PIN не обходить активне блокування.

PIN зберігається лише як солоний scrypt-хеш у БД. Значення не передається в URL, не записується в Git чи Android-константи. Резервна копія цієї таблиці також має бути зашифрована.

Успішний вхід атомарно передає `is_admin` підтвердженому запису й знімає права з попереднього. Унікальний частковий індекс забороняє двох адміністраторів. Відкликання через `admin_enroll --revoke` також скасовує підтвердження для наступного входу.

## Межі компонентів

- UI: `android/.../ui/AdministrationScreen.kt`; не читає БД і не містить секретів.
- HTTP-контракт: `GET/POST /admin/access`; використовує штатну автентифікацію інсталяції.
- Політика PIN: `app/src/avelren/admin_pin.py`; незалежна від HTTP та PostgreSQL.
- Серверний доступ: `admin_access_api.py`; лічильник і час блокування зберігаються в PostgreSQL.
- Підтвердження власником: `admin_approve.py`; немає публічного маршруту підтвердження.

Міграція функції необов'язкова для запуску старого API, collector і notifier. Маршрут Admin окремо перевіряє точний запис `011_admin_access`; без нього повертає `unavailable`. Повна перевірка міграцій і відновлення перевіряє таблицю, індекс і безпечного власника функції.

## Перед розгортанням

Потрібні окремий дозвіл на серверні зміни, підтверджена резервна копія та перевірений порядок переходу прав PostgreSQL. Не запускати загальне оновлення compose як спосіб обійти ці передумови.

`011_admin_access.sql` створено від поточної основної гілки після 010. У незлитих старих гілках існують інші кандидати з номером 011. До злиття слід узгодити одну послідовність; не копіювати ці файли разом. Жодна застосована міграція не змінювалася.

Спочатку перевірити повний TimescaleDB adoption/restore-прогін, зокрема сценарії відкату після додавання нових об'єктів. Вузькі локальні тести на PostgreSQL цього не доводять. Розгортання не вважається дозволеним або готовим лише через успішні unit-тести.

Перехід прав 010 і нова функціональна міграція 011 — окремі фази. У межах adoption застосовувати лише точний префікс 001–010: його зворотний план не видаляє об'єкти майбутніх міграцій. Лише після успішного завершення переходу прав та його перевірок дозволено застосовувати 011. Повний набір міграцій окремо перевіряється звичайними backend- і restore-тестами; виключати 011 з цих перевірок не можна.

Після погоджених міграцій оператор під власними дозволеними обліковими даними виконує:

```text
python -m avelren.admin_approve <підтверджений-UUID-інсталяції> --set-pin
```

PIN двічі вводиться приховано через термінал; його не передають аргументом команди. При наступному перевстановленні виконується команда з новим перевіреним UUID без `--set-pin`. Вона не скидає лічильник і блокування. Для зміни PIN також потрібен окремий дозвіл власника; зміна PIN не скидає блокування.

## Перевірки

- Android: компіляція й unit-тести, включно з GET/POST, заголовками автентифікації, забороною PIN в URL і відмовою сервера.
- Політика: 7 тестів, зокрема третя помилка, точна межа 24 годин та правильний PIN під блокуванням.
- PostgreSQL: окремий набір `app/admin_tests`; тільки нова локальна БД з назвою `avelren_admin_test*` та явним дозволом `AVELREN_ADMIN_TEST_DB=1`. Це не повний прогін історії TimescaleDB.
- CI: Android-зміни запускають Android-перевірки; серверні — серверні; спільні й невідомі шляхи запускають обидва набори. Підсумковий `checks` не приймає пропуск потрібної перевірки.

У GitHub необхідно окремо перевірити фактичний прогін і налаштування захисту гілки. Цей документ не стверджує, що новий CI вже виконався або став обов'язковим.
