# Admin і видалення через 90 днів: підготовка розгортання

Статус: код/перевірки, **не розгорнуто**. 24.09.2026 власник явно доручив
увімкнути очищення через 90 днів, після перевірки оновити живу політику,
а також завершити Admin. Повторно просити загальний дозвіл на ці задачі
не потрібно. Перед змінами залишаються перевірки нижче; окремі процедури
зміни прав БД виконуються за їхнім конкретним перевіреним планом.

## Поточна перешкода — 24.09.2026

- Дві спроби SSH до перевіреної адреси завершились `Connection timed out`
  на TCP 22, ще до автентифікації. Локальний SSH-alias веде на той самий
  host/port, альтернативного налаштованого входу не знайдено.
- DNS відповідає очікуваній адресі. HTTPS `/api/health` повернув 200,
  `status=ok`, вік спостереження 44 секунди. Недоступність SSH не означає
  зупинку API або collector.
- Власник повідомив про зникнення роздачі інтернету; причину SSH timeout
  поки не встановлено. Повторити після відновлення мережі; за потреби
  діагностувати через консоль провайдера, без довільного reboot.
- На head `65dc0a01e7598bb7caa48f18825addb16c2a6526` пройшли всі шість CI,
  включно з ізольованими API/БД і restore. Це не замінює перевірки актуальної
  production-копії: читання remote backup було перерване SSH disconnect.
- Очищення, Admin і новий серверний прогноз ще не ввімкнені. Політика
  `/privacy` ще не змінена; її підготовлений HTML — `ops/static/privacy-policy.html`.

## Відомий стан

- Production API повертає 404 для `/admin/access`, хоча Android уже має новий вхід.
- У production за останнім аудитом застосовані лише 001–009. Перед змінами це
  звірити заново з журналом, фізичною схемою, ролями та override Compose.
- У репозиторії є Admin 011 із підтвердженням інсталяції, PIN, трьома спробами
  і добовим блокуванням. Існуючі інтеграційні тести перевіряють перехід із 009.
- Нова 012 додає фіксоване очищення `last_seen < now() - 90 days`.
  Застосовані міграції не редагувалися. Нових таблиць/послідовностей немає.

## Механізм 90 днів

- Функція `prune_inactive_devices(false)` лише рахує кандидатів; `true`
  видаляє не більше 500 за транзакцію. Параметрів строку чи пристрою немає.
- EXECUTE має тільки notifier і власник migrator; API/collector/watchdog/backup
  не можуть викликати функцію. Notifier не отримує прямий DELETE devices.
- Команда `python -m avelren.device_retention` — dry-run. `--apply` — до 20
  пакетів, максимум 10 000 записів за запуск. Неповне очищення дає ненульовий
  код, а не мовчазний успіх. У журналі лише кількості, без ID/FCM/PIN/DSN.
- Дочірні підписки, цілі й сповіщення прибираються чинними FK CASCADE.
  Прострочений Admin теж видаляється; approval очищається через SET NULL,
  а PIN, лічильники спроб і блокування не скидаються.
- Успішна автентифікація оновлює last_seen. Блокування рядка захищає від
  одночасного видалення під час такої активності; cleanup пропускає зайняті рядки.
- Timer о 04:00 UTC. Видалення застосунку саме по собі сервер не бачить;
  відлік іде від останньої автентифікованої активності. Public workload-запит
  без ідентифікації не є активністю конкретного пристрою.

## Перед окремою командою GO

1. Зберегти точні image IDs, source hashes, Compose base+override та чинні
   локальні правки. Ніколи не використовувати `latest` як доказ активного образу.
2. Перевірити свіжий encrypted backup, remote SHA/gzip і ізольоване відновлення
   через штатний restore. Не робити restore робочої БД для перевірки.
3. Відтворити production 009 + поточні ACL в ізольованій БД; прогнати 010–012,
   Admin-вхід, cleanup, backup-role pg_dump. Adoption 010 має свій forward/
   inverse runbook; не знімати pin 001–009 командою загального compose up.
4. Підготувати immutable API image лише з потрібними Admin-модулями й авторизацією;
   notifier image — з `device_retention.py`. Зберегти решту коду активного образу.
   Не замінювати неперевірені collector/watchdog/telemetry.
5. Незалежно звірити інсталяцію власника після перевстановлення телефона.
   PIN власник вводить локально через getpass; не передає в чат чи аргументах.
   `admin_approve --set-pin` не скидає lockout; не призначати довільний пристрій
   лише тому, що він останній у БД.
6. Показати власнику перелік міграцій, конкретні заміни контейнерів, dry-run
   кількість записів, що підлягають видаленню, і попросити окремий дозвіл.

## Після погодження

Виконати затверджений adoption runbook 010, штатні 011–012, звірити SHA й
schema contract. Recreate тільки погоджених API/notifier, збереження default
override і секретів, без запуску migrate/collector побічно. Спочатку dry-run
очищення; лише після підтвердження результату — одноразовий apply і timer.

Перевірити правильний/неправильний PIN, чужу інсталяцію, лічильник і блокування,
вхід власника, роботу collector й резервування. Політику про 90 днів публікувати
лише після підтвердженої роботи timer. Ніякого масового push у цьому етапі.

## Відкат і restore

### Адресат щоденного звіту: read-only аудит 24.09.2026

- Прочитано код фактично запущеного watchdog: `_notify` отримує адресатів
  тільки через `WHERE is_admin AND fcm_token IS NOT NULL`, без broadcast.
- На момент перевірки в production рівно один admin і один його push-токен;
  звичайних записів із тим самим токеном немає.
- Push-токен підключеного телефона порівняно за SHA-256 без виведення токенів.
  Знайдено рівно один відповідний запис, але `is_admin=false`.
  Нова інсталяція після перевстановлення зараз не є адресатом звіту.
- Потрібно окремо погодити перенесення адмінських прав на цю перевірену
  інсталяцію, відкликати попереднє призначення та перевірити доставку власнику.
  Сам аудит прав не змінював і push не надсилав. Ідентичність старого запису
  лише за кількістю admin не доведена; не вважати його автоматично поточним телефоном.

### Виправлення після перевірки 24.09.2026

- Restore після `pg_dump --no-owner` тепер повертає власника функції
  `prune_inactive_devices(boolean)` до `avelren_migrator`. Інакше функція
  SECURITY DEFINER залишалась у власності адміністратора відновлення,
  і перевірка схеми правильно відхиляла результат. Перевірку не послаблено.
- Фікстура повторної реєстрації отримала FCM-токен допустимої довжини;
  попередній короткий тестовий токен закономірно повертав 422 замість 201.
- Повторна повна ізольована restore-репетиція та API-тести мають пройти CI
  перед прийманням цих виправлень. Production не змінювався.

- Вимкнення timer припиняє нові видалення, але **не повертає видалені дані**.
- Після commit cleanup повернення старого image не є відкатом БД. Не обіцяти
  миттєвий rollback: потрібна окремо погоджена процедура відновлення, з ризиком
  втрати новіших записів. Спочатку ізольований restore і звірка, не live restore.
- Старий API image може працювати зі схемою 011/012 за перевіреним контрактом;
  міграційні файли та їхні SHA не редагувати й не видаляти.
- Після restore застарілі device-записи можуть повернутися з копії. До
  поновлення робочої обробки запустити retention на відновленій ізольованій БД,
  перевірити результат; той самий затверджений порядок потрібен при реальному restore.
