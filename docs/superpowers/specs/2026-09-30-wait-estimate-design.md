# Відсутня оцінка очікування: сумісний контракт

Дата: 30.09.2026. Статус: погоджена власником у чаті 30.09.2026.
[План реалізації](../plans/2026-09-30-wait-estimate.md) підготовлений для
окремого перегляду перед кодом.
Погоджений напрям: сумісне розширення, без переписування історичних
спостережень і без побічної зміни політики призупинених КПП.
Цей документ не є реалізацією або дозволом на deployment.

Пов'язано: [ORIGINAL #70](https://github.com/ikstv/AvelRen-ORIGINAL/issues/70),
[legacy #111](https://github.com/ikstv/AvelRen/issues/111),
[залишки перенесення](../../MIGRATION-REMAINING.md),
[готовність релізу](../../RELEASE-READINESS.md).

## Мета й межі

Не змішувати відсутню оцінку з виміряним нулем. Зберігати кількість авто
та успішне спостереження, навіть якщо wait_time відсутній або null.
Кількісний прогноз не повинен залежати від достатності wait-історії.
Старий APK повинен декодувати відповідь нового сервера; новий APK має
працювати і зі старим сервером.

Не змінюємо upstream endpoint, заголовки, Device ID, вантажний scope,
60 секунд між початками циклів, політику HTTP-помилок або частоту запитів.
Модель кількісного прогнозу та її точність не поліпшуються самі собою
від зміни семантики; незалежна перевірка якості залишається обов'язковою.
Google Drive залишається backup-сховищем, не джерелом online-прогнозу.

## Вихідні факти

У перевіреному main після PR #68 модель має wait_time: int = 0.
Відсутнє поле стає 0; явний null відхиляється. db.py записує лише число.
observations_hourly агрегує всі wait-значення; API та прогноз обходять
частину неоднозначних нулів фільтрами сирої історії.

Android вимагає числові wait_time_seconds і wait_seconds_*.
Кількісна модель читає всі авто, але фінальна точка forecast.points
вимагає також достатньої wait-історії. Факти відтворення та посилання
на код зафіксовані в #70. Нову звірку production цей документ не містить.

## Збереження спостережень

Нова послідовна міграція додає до observations колонку
wait_time_status зі значеннями reported, missing, legacy_unknown.
Default — legacy_unknown, щоб старий collector після відкату залишався
працездатним і не позначав свої записи як підтверджені новим контрактом.

Чинна wait_time_seconds лишається NOT NULL для сумісності:
reported зберігає передане невід'ємне число, missing зберігає технічний 0.
У новому коді число не читається без стану. CHECK обмежує дозволені
стани, вимагає 0 для missing та невід'ємне число для reported.
Старі значення, включно з невалідними, не переписуються під нові вимоги.

Новий collector завжди явно записує статус. Відсутній ключ або null
означає missing; явний валідний 0 означає reported з числом 0.
Невід'ємний JSON integer приймається; bool, дробове число, рядок і
від'ємне число є помилкою формату, не missing. За збереженою політикою
валідації цикл записує parse-помилку в collector_runs і не записує
частково провалідовану відповідь. Прийняття раніше примусово приведених
типів є окремою сумісністю джерела: перед реалізацією перевірити
наявні збережені фікстури, без нового запиту до upstream.

Жодного UPDATE історичних спостережень чи декомпресії для backfill.
Додавання колонки до compressed hypertable має бути підтверджене
на ізольованій БД і чинній production-версії TimescaleDB; підтримку DDL
не припускаємо. Якщо тест не проходить, цей дизайн повертається на
перегляд, а не застосовується до production.

Уточнення, погоджене власником 30.09.2026 після CI-блокера: міграція
015 не призначена для TimescaleDB 2.17.2. Ізольована репетиція починає
зі схеми 001–014 на 2.17.2, доводить backup/restore і незмінність даних,
оновлює image та extension до 2.30.1, і лише потім застосовує 015.
Після цього знову перевіряються дані, старий журнал і backup/restore.
Це погодження тестового порядку, не дозвіл оновлювати production.

## Правила читання

Для нового контракту reported означає точне передане значення, включно
з 0. Для missing оцінка null. Для legacy_unknown позитивне число
можна використовувати з явним legacy_unknown; історичний 0 залишається
null: вже неможливо довести, чи було поле присутнє.

Нова wait-історія та wait-прогноз використовують reported, включно з
нулем, і позитивні legacy_unknown. Missing і неоднозначні старі нулі
не тренують wait-модель. Кількісна історія зберігає всі валідні
vehicles_in_queue незалежно від статусу wait.

Позитивний wait на paused-КПП залишається доступним для ETA та
сезонної wait-історії, як у поточному коді. ETA для paused із нульовим
wait не генерується. Решта змін paused-політики поза цим scope.
Reported 0 на непризупиненому КПП не підмінюється missing через
кількість авто: новий контракт використовує ознаку, а не евристику.

Момент ETA — час спостереження плюс дозволена оцінка, ніколи не прогноз.
Точність чи фізична достовірність upstream-оцінки цим не гарантується.

## Сумісне API

Зберігаємо назви й числові типи старих полів. Старі точки
forecast.points залишаються legacy-проєкцією з чинним gate достатності
wait-історії; у них не вставляємо нульовий wait замість відсутнього.
Старий workload.entry_eta зберігає чинне правило suppression нулів;
новий клієнт не використовує його як підтвердження нового контракту.

До workload додається wait_estimate:

- status: reported, missing або legacy_unknown;
- seconds: nullable integer за правилами читання;
- entry_eta: nullable ISO timestamp за правилами ETA вище.

До forecast додається count_points: масив доступних результатів
predict_counts незалежно від wait-слота. Кожна точка містить time,
vehicles_low, vehicles_expected, vehicles_high, calibration_samples
і wait_estimate. Тут wait_estimate — null, якщо wait-слот недостатній,
або об'єкт seconds_low, seconds_expected, seconds_high, samples.
samples означає число придатних погодинних повторів, а
calibration_samples — число сусідів кількісної моделі: не змішуємо їх.

Ті самі readiness, 12-тижневе вікно, актуальний вимір до 3 хвилин і
причина fresh_measurement_required зберігаються. Наявність count_points
не обходить readiness або MIN_NEIGHBORS.

Новий workload об'єкт є описом оцінки джерела; об'єкт у count_points
є прогнозом і показується як прогноз, не як entry_eta.

Сирий history отримує wait_time_status і nullable wait_estimate_seconds.
Для погодинного history додаються незалежні count_hours і wait_hours
поряд зі старим points. count_hours: time, avg_vehicles, samples
по всіх валідних кількостях; wait_hours: time, avg_wait_seconds,
max_wait_seconds, samples лише по придатних wait-оцінках.
Не замінюємо типи старого points і не зменшуємо кількісну історію
через фільтр wait. Legacy-projection залишається відокремленою.

observations_hourly з 001 не редагуємо. Нові читачі використовують
явні SQL-проєкції сирих observations з новим статусом, як чинний
workaround; новий continuous aggregate не входить до цього кроку.
Перевіряємо план і час SQL, щоб нове читання не створило деградацію.

Quality endpoint і незалежний backtest мають явно називати оцінювану
модель; новий статус wait не дозволяє видавати seasonal MAE за оцінку
current_anchored_neighbors_v1. Held-out тиждень, справжній MAE=0
і відсутність train/validation leakage зберігаються.

## Android

Нова DTO зберігає legacy-поля та додає nullable нові об'єкти.
count_points у DTO nullable без ототожнення null і порожнього масиву:
null означає старий сервер і fallback до points; [] означає
новий контракт без доступного прогнозу, а не привід оживити legacy points.

Коли workload.wait_estimate присутній, UI показує missing або
невідомий legacy-нуль як «Оцінка очікування відсутня», а reported 0
як «0 хв очікування». Позитивний legacy_unknown не видається за
нову підтверджену оцінку: підпис «За історичними даними».
Час в'їзду береться з нового об'єкта, якщо він присутній.

Якщо нових полів немає, зберігаємо поточний legacy-показ без твердження
про підтверджений нуль. Прогноз кількості показуємо навіть без
wait_estimate. Кольори ROAD SIGN та інші екрани не змінюємо.

## Перевірки й поетапне приймання

1. Unit/HTTP mock: omitted, null, 0, позитивне, bool, дробове, рядок,
   від'ємне; цикли й primary/derived error contract. Без upstream.
2. Ізольована TimescaleDB: всі попередні checksum незмінні; нова
   колонка та constraints; compressed chunks; старий collector insert
   без статусу; права сервісних ролей та backup.
3. API/ETA: missing ніколи не породжує новий ETA; reported 0 та
   paused сценарії; новий та старий JSON; незалежні count/wait history.
4. Forecast: count-only точки, gate readiness та fresh anchor,
   достатність кожного wait-слота, окремі samples, MAE=0 та holdout.
5. Android: старий/новий сервер, null/[] для count_points,
   декодування старим клієнтом, нові підписи й часові пояси.
6. Backup/restore: зашифрована синтетична копія в ізольованому проєкті,
   Timescale pre/post hooks, schema/ownership/allowlist та cleanup.
7. Review і CI відповідних компонентів на точному head. Потім merge,
   clean-main build і окреме телефонне приймання з SHA-256.
8. Production лише після окремого GO та свіжої перевірки pin/override,
   усіх активних образів, прав, backup/restore і способу відкату.

Не редагуємо застосовані міграції. Номер нового файла визначається за
main на момент реалізації (на зрізі аудиту остання 014), не резервується
навмання. Новим таблицям/послідовностям потрібні явні SELECT grants
avelren_backup; якщо не створюються нові об'єкти, все одно перевіряємо
повний backup і schema contract. Provenance оновлюється без стирання
історичних доказів перенесення.

## Відкат і ризики

Схема додається до розгортання нового collector; API й Android
розширюються сумісно. Старий collector може писати legacy_unknown.
Відкат застосункових образів не видаляє колонку, дані або журнал
міграцій; перевірки схеми старого runtime повинні бути протестовані
з розширеною схемою. Якщо вони відхиляють її, відкат лише образів
не вважається підтвердженим і deployment не дозволяється.

Стиснена історія, strict source parsing, час SQL, старі schema gates
та Android fallback — конкретні acceptance gates, не припущення.
DDL і production rollback-процедура оформлюються в implementation plan
після перегляду цієї специфікації. Відновлення backup не виконується
автоматично як відкат.

## Межа готовності

Специфікація не закриває #70/#111 і не підтверджує точність прогнозу,
CI реалізації, deployment, APK, телефон чи Play. Всі ці стани ведуться
окремо в RELEASE-READINESS. Після перегляду власником готується
план реалізації; до цього product-код і міграції не змінюються.
