# Повернення Admin-доступу після перевстановлення за PIN

Дата: 26.09.2026. Статус: дизайн для review власника.

## Мета і причина

Після перевстановлення власник вводить чинний чотиризначний PIN і знову отримує Admin без ручного схвалення нового ID. Власник погодив, що правильний PIN на іншому телефоні також дає доступ: тотожність апаратного пристрою не перевіряється.

Зараз DeviceStore зберігає device_id і device_secret лише в локальних EncryptedSharedPreferences, а Android manifest має allowBackup=false. Після видалення застосунку пара зникає. InstallationRepository реєструє новий ID, але admin_access.approved_device_id вказує на старий. API повертає awaiting_approval і не приймає PIN. FCM-токен не є доказом права на Admin.

## Поведінка

- Кожна автентифікована інсталяція з FCM-токеном бачить форму PIN, якщо Admin налаштовано й блокування немає. GET не витрачає спробу і не переносить право.
- POST перевіряє чинний scrypt-v1 PIN. Три неправильні спроби сумарно для всіх інсталяцій блокують Admin-вхід на 30 днів від третьої спроби. Лічильник у БД не скидається перевстановленням, новим токеном чи IP.
- Під час глобального блокування навіть правильний PIN не входить. Чинний devices.admin_blocked_until конкретної інсталяції також діє до завершення.
- Правильний PIN у єдиній транзакції скидає лічильник, переносить approved_device_id, знімає is_admin зі старої інсталяції та ставить новій. У БД залишається щонайбільше один Admin. Інсталяція без FCM-токена не може стати адресатом Admin-сповіщень.
- Старий пристрій зберігає звичайні можливості за власними credentials, але втрачає Admin.

## Технічний дизайн

Нова міграція 014 додає вузьку SECURITY DEFINER функцію перенесення Admin. Її власник — avelren_migrator, search_path зафіксований, EXECUTE має тільки avelren_api, PUBLIC не має доступу. Функція під блокуванням admin_access перевіряє глобальний lock і FCM-токен кандидата, потім атомарно переносить approval та is_admin. API викликає її лише після успішної Python-перевірки PIN у тій самій транзакції. API-роль не отримує прямого UPDATE цих полів. schema_verify перевіряє власника, режим і права функції; backup-роль зберігає читання.

admin_access_api.py прибирає вимогу попереднього approval для PIN-входу, але зберігає автентифікацію device_id + device_secret, окремий блок конкретної інсталяції та fail-closed поведінку без міграції 014. Спільний лічильник admin_access.failures/locked_until захищений row lock перед перевіркою PIN. admin_pin.py встановлює 30 днів. Без 014 новий API не відкриває PIN-вхід іншим інсталяціям.

Android використовує InstallationRepository і Api.adminAccess. Екран Admin показує форму PIN для нової інсталяції в стані ready, а після authorized — Admin-статус. PIN не зберігається на диску, не перевіряється локально й передається лише в тілі POST.

## Безпека та відкат

Чотиризначний PIN стає єдиним доказом права перенесення. Той, хто знає PIN, може перенести Admin на свій телефон. Будь-яка інсталяція може навмисно витратити три спроби й заблокувати власника на 30 днів. Це наслідки погодженого контракту; IP rate limit не замінює глобальний лічильник.

Штатний host-side admin_approve залишається, але не скидає глобальний lock. Аварійне розблокування — лише окрема перевірена host-side операція з явним дозволом; HTTP endpoint не додаємо. Застосовані міграції 001–013 не редагуємо. Старий API з новою схемою працює за старими правилами. Production deployment потребує перевіреного backup, звірки схеми й ролей, точного image pin та окремого дозволу.

## Перевірки і приймання

- Unit: третя помилка дає 30 днів; правильний PIN не обходить lock; повторний запит не продовжує строк.
- Ізольовані DB/API тести: нова інсталяція бачить форму, хибний PIN не переносить права, правильний переносить їх рівно одному пристрою, старий Admin втрачає право, FCM-адресат стає новим.
- Конкурентні спроби не обходять ліміт; перевстановлення не скидає спільний лічильник; окремий старий блок діє до expiry.
- Ролі й backup: API має тільки вузький EXECUTE без прямого UPDATE approval/is_admin; backup читає потрібні об'єкти; rollback попереднього API працює з 014.
- Android JVM: ready, authorized, blocked; PIN лише в тілі запиту без локального збереження.
- У RELEASE-READINESS.md окремо вести код, CI, deployment, APK, телефонний сценарій після перевстановлення, SHA-256 установленого APK і Play.

Одноразове схвалення нинішньої інсталяції на production уже виконане штатним admin_approve. Воно не доводить роботу майбутнього PIN-only механізму.
