# Пропозиція: безпечне володіння FCM-токеном і відновлення Android

Дата: 12.10.2026. Прочитаний checkout: `C:/AI/AvelRen/original-collector-pacing`, точний HEAD `eed0cb0f5a337e88467943017bbca3a04d2593e2`. Це проєкт контракту для погодження; продуктовий код, Git, production та Firebase не змінювалися. Інший виконавець окремо виправляє notifier. Запропоновані нижче тести ще не виконувалися.

## Мета і підтверджена причина

Знання чужого FCM-токена не повинно змінювати його серверного власника, відкривати підписки чи повертати чужі credentials. Водночас справжній Android-клієнт після перевстановлення, втрати secret або відновлення БД має самостійно отримати працездатну нову реєстрацію доставки. Нової системи облікових записів не додаємо.

`subscriptions_api.create_device()` зараз обнуляє токен іншої installation перед INSERT. `update_token()` робить те саме перед UPDATE. `UNIQUE(fcm_token)` гарантує лише одного власника, але поточний код дозволяє чужому запиту відібрати доставку. `test_auth.py::test_repeat_registration_with_known_token_does_not_leak_device_id` перевіряє credentials/підписки, але не збереження токена жертви.

Android уже централізує recovery у `InstallationRepository`, зберігає pending token та використовує WorkManager. Проте `409` зараз terminal; `FcmTokenProvider` уміє лише читати token; `registerFreshLocked` очищує credentials до POST; `authenticatedCall` і token worker можуть незалежно входити в recovery. Один лише серверний `409` зупинить законне відновлення.

## Варіанти

| Варіант | Що робимо | Компроміс |
|---|---|---|
| **A — рекомендований** | Сервер відхиляє зайнятий токен без зміни власника; Android змінює власний Firebase registration token і повторює запит. | Мінімальна зміна API, без міграції БД; потрібні стійкий Android recovery і погоджена втрата доступу до старих підписок після втрати secret. |
| B — відокремлена реєстрація | Android завжди спершу створює installation без токена, зберігає credentials, потім прив'язує token через PUT з тим самим правилом конфлікту/ротації. | Сервер уже приймає null; краще розділяє identity та push readiness, але змінює всі шляхи старту й потребує окремого видимого стану доставки. Не усуває неоднозначність втраченого POST response без нового idempotency-протоколу. |
| C — підтвердження через доставку | Зберігаємо старого власника до одноразового FCM challenge, після підтвердження дозволяємо лише перенесення доставки; credentials/підписки не переносимо. | Нові challenge API, таблиця, TTL, rate limits, захист replay, залежність від фонової доставки. Значно більше коду й ризиків; для цього виправлення не рекомендується. |

Варіант A закриває саме викрадення вже прив'язаного токена. Він не доводить право першого заявника на ще вільний токен; такий доказ потребує окремого протоколу на кшталт C. Не називати знання токена автентифікацією.

## Рекомендований серверний контракт

1. `POST /devices`: відсутній/вільний token → `201` і **нова** пара; уже прив'язаний до будь-якої installation token → `409 {"detail":{"code":"fcm_token_conflict"}}`. Жодної нової installation і жодних змін попереднього власника при конфлікті. Не повертати owner ID, token, secret, capabilities або subscription data.
2. `PUT /devices/token`: спочатку чинна перевірка credentials; вільний token або token цього самого device → `200`; token іншого device → той самий `409`. При конфлікті зберегти обидві прив'язки, credentials, capabilities, підписки й права Admin. `401` залишається виключно проблемою credentials; `409` ніколи не запускає очищення валідних credentials.
3. Не виконувати `UPDATE ... WHERE fcm_token=...` для іншого власника. INSERT/UPDATE і capabilities — одна транзакція. Усі API-операції присвоєння непорожнього token беруть transaction-scoped advisory lock за стабільним 64-bit digest кандидата, потім перевіряють власника й виконують зміну. Сирий token не є lock key; випадкова колізія digest лише серіалізує незалежні запити. Вільний token між такими API-запитами не можна захопити в проміжку SELECT/UPDATE. Остаточний інваріант усе одно забезпечує чинний unique constraint. Для INSERT придатний `ON CONFLICT (fcm_token) DO NOTHING RETURNING id`; для непередбаченої гонки UPDATE — вузьке перехоплення `UniqueViolation` саме constraint токена після rollback/savepoint. Не перетворювати всі integrity errors на `409`. Взяття лише lock кандидата перед lock свого device виключає зворотний порядок захоплення двох token locks; перевірити це реальними race-тестами під API role.
4. Після перевірки credentials `_device()` відпускає своє row lock до другої транзакції. UPDATE повинен мати `RETURNING id` і перевіряти реальний результат; якщо row видалено між auth та UPDATE, повернути `401`, не помилковий `200`. Якщо буде перевірка hash у тій самій транзакції, не дублювати сторонні зміни auth як рефакторинг у цьому PR.
5. На конкурентних POST/PUT допустимі визначені `201/200/409`; timeout БД → чинний retryable `503`, але не SQL traceback чи token у відповіді/журналі. Значення токена є в PostgreSQL duplicate-key diagnostics: не логувати exception/params, а передбачувані конфлікти обробляти до SQL exception під advisory lock. Саме перехоплення Python exception не приховує PostgreSQL server logs; перед deployment перевірити parameter/error logging та існуючий global `OperationalError` logger (він нині пише `exc`). Це конкретна межа перевірки, не твердження, що поточні DB logs уже безпечні. Метрики — лише лічильники типів операцій/результатів.
6. Рівно та сама поведінка незалежно від віку installation, null secret, Admin, active subscriptions, `last_seen` чи client version. Не додавати «перенесення після N днів» або небезпечний fallback для старих APK. Конфлікт повідомляє лише непридатність поданого токена; це обмежений membership oracle, але без identity/data.

## Android: один координатор recovery

**Конфлікт за чинних credentials.** Зберегти ту саму пару й усі підписки. Відновити лише транспорт: obtain replacement token, PUT з тією самою парою, і лише після успіху очистити pending. `InstallationState.Ready` означає доступ до API; при невідновленій доставці потрібен окремий мінімальний стан push sync/error, щоб UI не обіцяв справність сповіщень.

**Немає credentials або отримано 401.** Чинний single-flight recovery створює нову installation. Якщо POST відхиляє повторно використаний token, виконати ту саму ротацію й новий POST. Жодного пошуку installation за token. Серверні старі підписки, ETA, surge та Admin не переносяться; доступні лише дані нової installation. Існуючий оригінальний authenticated call повторюється щонайбільше один раз після успішного recovery; другий 401 не створює нескінченну реєстрацію. Відновлені з backup credentials, які сервер ще приймає, зберігаються навіть при конфлікті токена. Прибрати безумовний `store.clear()` перед POST: очищувати лише конкретну пару, для якої підтверджено 401; невдалий POST/409 не може знищити валідну пару, яку паралельний recovery уже зберіг.

**Втрачений response POST.** Сервер міг уже створити рядок, але клієнт не має secret. Повторний POST може повернути 409; безпечно виконати ротацію та створити іншу installation. Невідомий secret не відновлюємо й не передаємо старі підписки. Можливий orphan лишається під чинною retention; це прийнятий компроміс A, не гарантія exactly-once.

**Стійка послідовність.** Розширити provider операцією ротації для поточного Firebase app instance. Для зафіксованого Firebase BOM `33.7.0` очікуваний seam — `deleteToken().await()`, потім `token.await()`. Не видаляти Firebase Installations ID і не оновлювати SDK побічно. Поточна офіційна документація вже описує новий opt-in API, тому доступність використаних методів остаточно звірити компіляцією з locked залежностями. Документація підтверджує, що deleteToken стосується registration token цього Firebase project, а FID не видаляє; не обіцяє конкретний строк отримання іншого значення. [FirebaseMessaging reference](https://firebase.google.com/docs/reference/android/com/google/firebase/messaging/FirebaseMessaging).

Зберігати в encrypted preferences одну атомарну pending recovery record: generation, candidate/rejected token та phase (`sync`, `rotate`, `fetch_after_delete`), без запису в logs/WorkManager input. На 409 durable record переходить у `rotate`; перед видаленням перечитати provider: якщо current уже відрізняється від відхиленого token, використати його без видалення. Після успішного delete durable phase стає `fetch_after_delete`; помилка getToken повторює fetch, а не delete. Повернення того самого відхиленого token не дає дозволу повторювати API в гарячому циклі: лишаємо recovery pending з backoff. Crash між delete і записом phase допускає повторний безпечний цикл відновлення, але ніколи не захоплення серверної прив'язки.

Бюджет одного recovery incident — **одна завершена автоматична ротація** та одна негайна спроба прив'язати replacement. Кількість завершених ротацій зберігається в record і не скидається worker retry/startup. Новий конфлікт replacement після витрати бюджету → durable `conflict_blocked`, видимий стан затримки доставки та завершення поточного worker без подальших автоматичних delete/POST циклів; явно запущений користувачем повтор або новий provider token дозволяє спробу синхронізації. Новий token не обнуляє бюджет incident до успішної прив'язки; успіх закриває incident. Firebase/network outage, `408/429/5xx`, помилка durable commit/enqueue → зберегти фазу та retry з наявним exponential backoff. Timeout delete неоднозначний: перед повтором reread provider, щоб не видалити вже отриманий replacement. Інший `409`, `400/403/422` не запускає ротацію. Скасування coroutine прокидати далі, без очищення durable record. Відсутність іншого token після delete повторює тільки fetch з backoff, не нові delete.

**Конкурентність.** Усі registration/token mutations (`initialize`, callbacks, worker, currentOrRegister, 401 recovery) проходять один визначений coordinator/gate. Не вкладати старі mutex у взаємно протилежному порядку. `onNewToken` має бути сигналом синхронізувати актуальний provider token; callback зі старим X не може перезаписати Y після ротації. Читання provider, phase transitions і generation мають узгоджуватись; результат старого in-flight запиту не публікує нові credentials і не очищує новішу generation. Durable clear — CAS за generation/phase, не тільки рядком token. Синхронізація успішного X не означає успіх усього worker, якщо вже існує Y: drain pending або повернути retry.

Зберегти гарантію enqueue-before-HTTP. Під час внутрішнього recovery worker не повинен повторно викликати `enqueueUniqueWork(REPLACE)` і скасовувати сам себе: він продовжує поточний прохід/повертає retry. Новий callback спершу робить durable handoff, потім enqueue; enqueue failure залишає роботу для startup/resume. Успішне збереження credentials перед Ready теж зробити підтвердженим durable commit: нинішній `apply()` не повідомляє про запис. Виправлення стосується тільки identity/recovery records, не всіх preferences.

## Сумісність і випуск

- Нової міграції PostgreSQL не потрібно: `devices.fcm_token UNIQUE` вже існує в 004, права API достатні. Застосовані міграції не редагувати. Новий durable Android record мігрує старий `pending_fcm_token` атомарно без втрати роботи. Downgrade під час recovery не обіцяти без окремої перевірки формату.
- Новий APK сумісний зі старим API за успішними запитами, але старий API все ще дозволяє викрадення token; саме оновлення APK не закриває серверний дефект. Новий API сумісний зі старим APK для вільного/власного token; при колізії старий APK не вміє recovery й може потребувати оновлення.
- Рекомендовано підготувати та перевірити обидві сторони до deployment; погоджено розгорнути захисний API, одразу випустити recovery-capable APK. Не залишати insecure server fallback на час rollout. Якщо терміновий server hotfix виходить раніше APK, явно прийняти тимчасову несправність recovery у старих клієнтів. Повідомлення про оновлення не може залежати тільки від FCM, який саме може не працювати.
- Production deployment, Android installation і Play publication — окремі дозволи за AGENTS.md; ця пропозиція їх не надає. Відкат не має повертати transfer-on-token: тримати захисне серверне правило й виправляти клієнт forward. У release readiness окремо: код/CI/API deploy/APK hash/телефон/Play.

## Необхідні перевірки

**Реальні API + PostgreSQL** у чинному isolated `scripts/test_database.sh`, під `avelren_api`, без зовнішньої мережі:

1. POST з token жертви → 409; точна кількість devices не змінилась; owner token/secret hash/capabilities/subscriptions/ETA/surge/Admin збережені. Credentials жертви працюють; чужі не дають доступу. Відповідь і захоплені логи не містять жодних секретів/token/owner ID.
2. PUT іншого device з token жертви → 409, обидві початкові прив'язки збережені. PUT власного й вільного token → 200. POST без token → 201. Invalid/missing credentials → 401 до token-conflict lookup.
3. Barrier-керовані **окремі DB connections/паралельні API requests**: два POST одного вільного token; POST проти PUT; два PUT різних devices одного вільного token; повторні PUT одного власника; спроба взаємного обміну зайнятими token. Рівно один власник, очікувані 2xx/409 без unhandled 500/deadlock, rollback capabilities повний. Не підміняти SQL фейками й не покладатися лише на sleep.
4. Видалення device між `_device` і UPDATE → 401; outage/timeout → 503 без token diagnostics. Після conflict транзакція/connection придатні для наступного API call.
5. Сценарій reinstall/secret lost: старий token →409; replacement →201; старі дані не переходять. Сценарій restored valid credentials: conflict → replacement PUT, identity/subscriptions залишаються ті самі. Старий AUTH-1 regression змінює очікування повторного POST з 201 на 409 і доповнюється власником token.

**JVM/Ktor MockEngine**: точне розпізнавання `409/detail.code`, 401 лишається окремим; successful/failed delete/get; same-token response; saved pending після process recreation у кожній phase; durable save/clear/enqueue failure; втрата POST response; token Y під час X PUT/rotation; пізній callback X після Y; worker cancellation REPLACE; паралельні 401 + token conflict; second 401 без loop; valid creds при 409 не очищуються. Перевіряти реальну repository state machine, не лише fake API counters. Firebase provider fake; реального FCM і ключів немає. Команда з README: `gradlew.bat -PavelrenUiPreview=true :app:testDebugUnitTest :app:compileDebugKotlin --no-daemon --max-workers=2`.

## Файли майбутньої реалізації та рішення власника

Сервер: `services/backend/src/avelren/subscriptions_api.py`, secret-safe logging відповідного DB error шляху в `api.py`, `services/backend/tests/database/api/test_auth.py` та окремі ownership race tests. Android: `InstallationRepository.kt`, `FcmTokenRetry.kt`, `FcmTokenSyncWorker.kt`, `DeviceStore.kt`, `Api.kt`, `AvelRenApp.kt`; їхні JVM-тести та маленький API contract test. Окремий delivery-state UI — лише в обсязі видимого recovery status, не redesign. Документація: API/Android README, актуальний аудит/план перенесення, `docs/RELEASE-READINESS.md`.

**Потрібне погодження нового recovery-контракту:** обрати A, включно з однією автоматичною ротацією на incident, видимим conflict state після її вичерпання та збереженням валідних credentials на PUT409. Чинна security boundary не змінюється: втрата `device_secret` уже сьогодні створює нову installation без відновлення старих підписок/Admin; token не може це дозволяти. Це треба пояснити користувачеві, а не представляти як нову втрату даних чи нову гарантію recovery. Також погодити rollout: API hotfix до доступного APK з тимчасовим обмеженням старих клієнтів чи скоординований випуск обох після перевірок. Рекомендація — A та скоординована підготовка, API першим.

Невідоме перед deployment: реальна частка/версії старих APK, фактична поточна production-схема/образ, поведінка Firebase rotation на підтримуваних телефонах. Нічого з цього не перевірялося live. Synthetic тести доводять контракт, а не доставку Firebase. Окреме телефонне приймання після дозволу має підтвердити rotation, offline/resume і збереження валідної identity; live FCM у цій роботі не виконується.
