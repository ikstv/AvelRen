# Відновлення прогнозу й діагностика джерела — 08.10.2026

## Підтверджений інцидент

Read-only аудит production: Чоп, API `/api/surge/17`, reason
`insufficient_history`, issued_at 19:00:21 UTC (22:00:21 Києва).
О 21:12:21 і 21:19:21 Києва collector_runs містили ConnectError/0 rows;
логи збирача уточнили `[Errno -2] Name or service not known` — DNS-помилка.
Наступні хвилини дали HTTP200/38 rows. Збирач не перезапускався,
RestartCount0/OOMKilledfalse. Визначити винний upstream DNS із цих журналів
неможливо; Docker resolver використовує host systemd-resolved.

Модель відхилила 60-хвилинний lag через пропуски; 120-хвилинний target
також був відсутній. О 22:22:46 Києва всі lags стали валідними й контрольний
розрахунок видав score. Записаний статус не оновився: worker позначав годину
розрахованою навіть за score=null і не повторював її до наступної години.

## Погоджене виправлення

Для кожного підтримуваного КПП, якщо останній прогноз цієї години не має
score, worker повторює розрахунок лише після нового свіжого спостереження.
Невдалі результати зберігаються, успішний результат припиняє повтори до
наступної години. Чинний checkpoint lock і унікальність prediction збережені;
це відновлює і записи, створені старою версією. Якість/покриття історії та
поріг моделі не послаблені. Нових запитів до джерела немає.

Транспортна помилка отримує обмежений запис:
`ConnectError: reason=dns errno=-2`. Причини: dns, tls, connection_refused,
network_unreachable, host_unreachable, connection_reset, timeout, os_error,
unknown. Беремо типи й errno з ланцюжка винятків, а не довільний текст.
Справжня тривалість невдалого запиту записується в duration_ms.
SQLite whitelist зберігає лише канонічний безпечний формат; старі записи
сумісні. Той самий error передається replay до collector_runs і в журнал.
HTTP-коди залишаються штатними HTTP-кодами. Схему spool/БД не змінено.
Ці коди визначають клас збою, але не доводять винного DNS-провайдера;
невизначеність явно зберігається як unknown.

## Межа підтримки КПП

Нинішня frozen модель навчена для ID 1,6,17,29: Ягодин, Краківець, Чоп,
Ягодин для порожніх вантажівок. Фактичне зростання підтримується для інших
вибраних КПП; прогноз Ужгорода не ввімкнений. Додавання ID до списку без
навчання/перевірки не підтверджує здатність прогнозувати інші переходи.
Розширення моделі — окрема робота. Ліміт 3 КПП на скріншоті відповідає
новішим Android-змінам з іншого ПК; це не причина unavailable.

## Приймання та розгортання

Регресії перевіряють усі 4 підтримувані ID, відновлення старого невдалого
запису, нове спостереження, один успішний прогноз за годину, паралельні
DB-транзакції та незмінну кількість епізодів. Mock HTTP перевіряє DNS/TLS/
відмову/мережу/unknown, тривалість і відсутність секретних canary у логах.
Окремий DB-тест перевіряє replay DNS-причини під collector role.

Код — кандидат. CI, встановлення worker/collector на production та фактичне
приймання ще ведуться окремо. Production-записів під час аудиту не було.
Перед встановленням потрібен конкретний application/collector план:
точні активні images, spool preflight/backup, узгоджений 60-секундний
інтервал перемикання єдиного collector, поточні Compose override/pin,
перевірка cycles/API та відкат до збережених контейнерів/images.
Немає підстав змінювати DNS-конфігурацію без додаткових доказів.
