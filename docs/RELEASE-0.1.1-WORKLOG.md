# Робочий журнал до релізу 0.1.1

> Живий перелік знахідок і кандидатних змін. Це не опубліковані release notes і не дозвіл на production deployment чи Google Play. Після випуску погоджений опис потрібно перенести до постійних release notes, перевірити незакриті пункти й видалити цей тимчасовий журнал. Секрети сюди не додавати.

## Ціль і правила

- Версія застосунку в поточному `main`: `0.1.1`, `versionCode 4`.
- Точний склад визначаємо за кодом чистого commit, який піде у збірку.
- GitHub Release, тег, APK/AAB та текст Play Console мають описувати ту саму збірку.
- Публікація в Google Play і будь-які зміни production — лише після окремої явної команди власника.
- Не вважати перенесений server source розгорнутим на production.

## Перевірка AI-кандидата (24.09.2026)

- У локальний релізний кандидат додано повноекранний погодинний екран прогнозу вибраного КПП. Він показує максимум серед годин, що залишилися до кінця поточного дня за `Europe/Kyiv`, і погодинні значення.
- API читає історичні спостереження з бази сервера; застосунок не звертається до upstream чи Google Drive. У відповіді показуються p25–p75 і число схожих годин, коли сервер їх надає. Для старої відповіді без цих полів Android не вигадує `0–0`.
- Формула кількості лишається сезонною медіаною такого ж київського дня тижня та години за попередні 12 тижнів. Зміна додає погодинні p25/p50/p75 і блокує окремий слот, якщо йому бракує повторів. Це не нова AI-модель і не доведене підвищення точності часу піку.
- `docs/forecast.md` фіксує обмежений backtest публічної API-історії. Експериментальний гібрид покращив MAE кількості на перевірених КПП, але не дав стабільного покращення пікової години; його не включено як production-формулу.
- У відокремленій локальній гілці `codex/release-0.1.1-candidate` Android `testDebugUnitTest` і `assembleDebug` пройшли 24.09.2026. APK SHA-256: `E6D8CED41D5B28E041FDD229E1C9E804C193029BCA64B684CE0C58563B31549A`. Це debug-артефакт із гілки-кандидата, не APK із чистого `main` і не файл для Google Play.
- Виправлено попередній звіт: у наявному `.venv` нового репозиторію успішно пройшли всі 183 серверні unit-тести, включно з трьома тестами прогнозу. Реальна SQL/DB інтеграція цим не перевірена. ### Результат роботи з формулою

Кандидат серверного розрахунку тепер бере свіжу поточну чергу та історичні
зміни схожих ситуацій. Реальна історія чотирьох КПП перевірена без звернень
до єЧерги; цифри, обмеження й відтворення — docs/forecast.md.
Для Чопа дослідницька MAE кількості 147.15 → 42.91 авто. Точність піку на
двох інших КПП погіршилася; незалежної фінальної перевірки немає. Це кандидат,
не доведена готовність. 188 серверних unit-тестів пройшли; новий SQL-тест
потребує CI. Сервер не змінено. Політика: текст про 90 днів підготовлено
в PRIVACY-DELETION-DRAFT.md, не опубліковано; механізм очищення ще потрібен.

### Причина затримки моніторингу

Read-only перевірка журналу API за 24.09.2026: реєстрація /devices 201 о
13:56:36 UTC, перший /subscriptions 200 о 13:58:26 UTC. У збережених
91 відповідях /subscriptions — HTTP 200. Caddy не надав access-записів
із тривалістю; це не доказ, що всі запити були швидкими. Журнал телефона
не охопив точний початок і не показав мережевого exception.
У коді встановленої версії `remember { DeviceStore.credentials(context) }`
утримував null до повторного створення екрана навіть після успішної реєстрації.
Виправлено: екран спостерігає installation.state, оновлює credentials і
перезавантажує моніторинг при Ready. Захищені запити йдуть через спільний
InstallationRepository з recovery після 401; два списки читаються паралельно.
Журнал узгоджується з цією причиною, але тривалість окремих запитів не виміряна.

Усі шість CI-перевірок b7c06c1 пройшли, включно з новим SQL/API сценарієм
188 поточних авто проти 37 історичних. Правка реакції на реєстрацію потребує
нового Android CI. Сервер не змінювався.
