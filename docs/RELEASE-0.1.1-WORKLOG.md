# Робочий журнал до релізу 0.1.1

> Живий перелік знахідок і кандидатних змін. Це не опубліковані release notes і не дозвіл на production deployment чи Google Play. Після випуску погоджений опис потрібно перенести до постійних release notes, перевірити незакриті пункти й видалити цей тимчасовий журнал. Секрети сюди не додавати.

## Ціль і правила

- Версія застосунку в поточному `main`: `0.1.1`, `versionCode 4`.
- Точний склад визначаємо за кодом чистого commit, який піде у збірку.
- GitHub Release, тег, APK/AAB та текст Play Console мають описувати ту саму збірку.
- Публікація в Google Play і будь-які зміни production — лише після окремої явної команди власника.
- Не вважати перенесений server source розгорнутим на production.

## Що звірено між репозиторіями (24.09.2026)

- У приватному [AvelRen-ORIGINAL](https://github.com/ikstv/AvelRen-ORIGINAL) є опублікований [реліз v0.1.0](https://github.com/ikstv/AvelRen-ORIGINAL/releases/tag/v0.1.0). Його тег вказує на історичний старий код `b9caa61` (Play `versionCode 3`), а не на новий Android-код. У релізу поки немає AAB/APK-вкладення.
- На GitHub ще немає релізу або тегу `0.1.1`. Цей файл створює журнал підготовки; він не створює тег чи реліз.
- Старий [PR #194](https://github.com/ikstv/AvelRen/pull/194) у `AvelRen` закритий зі злиттям. Він додав Admin-доступ із підтвердженням інсталяції та PIN, зміни Android/API й тестову офлайн-копію UI. Власний опис PR фіксує блокери на момент злиття: повний DB/restore CI, узгодження схеми з production, відсутній на production Admin API, відсутність автоматичної розсилки релізу та відсутність AAB у Play.
- У `AvelRen-ops` основні commits датовані 23–25 серпня: runbooks, інтеграційний контракт і backup/restore документація. Це матеріали експлуатації, не нові функції Android.
- У новому monorepo злиті PR #1–#5: backup/ops source (#1), серверне ядро й БД (#2), API/Admin/watchdog (#3), Android-клієнт (#4) та ізольована restore-репетиція (#5). Це вміст репозиторію, а не доказ розгортання на робочому сервері.
- Відкриті PR #6–#8 стосуються production runtime, systemd telemetry та аудиту restore orchestrator. Їхній код не включати до опису Android-релізу як уже випущену чи розгорнуту функцію.
- Локальна гілка підготовки прогнозу має незакомічені зміни Android UI/API і server forecast. Це поки не частина GitHub `main` і не частина підтвердженої збірки.

## Кандидатні server/ops зміни

- У новому репозиторії є перенесені collector, API, база даних, міграції, Admin, watchdog, telemetry, backup/restore інструменти та production Compose source.
- Міграція коду не означає, що зміни застосовані до production. Сервер, його БД, секрети та розгортання тут не змінюються.
- Аудит production від 23.09.2026 є датованим знімком: на той час collector збирав дані, але робочий сервер ще відрізнявся від monorepo. Перед будь-якою майбутньою серверною операцією потрібна нова read-only звірка й окремий дозвіл.
- Server/ops зміни описувати в Android release notes лише якщо вони справді потрібні користувачеві й підтверджено сумісний стан production.

> - Оновлено екран прогнозу черги: погодинна оцінка на сьогодні та орієнтовний час піку за київським часом.
> - Поліпшено показ стану сервера й актуальності даних.

Пункти про прогноз, плашку стану, список моніторингу й Play update залишаються кандидатами, доки відповідний код не ввійшов у чисту збірку та не пройшов потрібні перевірки. Не додавати сюди Admin, 90-денне видалення, push релізу чи «покращену точність AI» без підтверджень.

## Файли релізу

Поки не створені / не прикріплені:

- підписаний AAB для `versionName 0.1.1`, `versionCode 4` (ще не створений);
- SHA-256, commit і дата збірки в записі `dist/BUILD.txt`;
- за потреби APK для ручної перевірки на телефоні; локально зібраний debug APK не встановився поверх наявного застосунку через різний підпис і не є релізним артефактом;
- фінальний текст release notes, звірений із фактичним AAB.

Не прикріплювати ключі підпису, секрети чи конфігурацію Firebase.
