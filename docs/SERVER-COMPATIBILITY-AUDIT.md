Сервер зараз обслуговує запити й записує свіжі спостереження. Масового
розходження основного Python-коду з новим репозиторієм не виявлено.
Проте новий репозиторій **ще не є готовою заміною production**: не завершені
production-збірка, restore та перехід сервісів із legacy-superuser.

HTTP 500 — збій джерела, а не доказ падіння нашого сервера. Collector
зберіг кожен цикл і не порушував інтервал. Дані тих невдалих хвилин
відновити з джерела неможливо; не приховуємо їх за твердженням «помилок немає».

У PostgreSQL-журналі є п'ять діагностичних помилок SQL: синтаксис,
невідомі колонки та неоднозначний оператор. Два невдалі SELECT із полем
`last_seen` у health_alerts зроблені саме цим аудитом, виправлені на
`last_sent_at`; дані не змінювалися. Походження решти трьох цим аудитом
не доведене. Вони не супроводжуються зафіксованими derived-помилками чи
traceback застосункових контейнерів. Лічильник слова ERROR у загальних
логах не є числом аварій: він також знаходить HTTP «Internal Server Error».

Системні записи рівня error: 21 від ssh.service, 2 sshd, 1 init.scope.
Немає ознак OOM або I/O error у перевіреному вікні. Історичне питання
cloud-init після наступного reboot не закрите цим читанням журналу.
Запис daily_status доводить прийняття FCM за логікою watchdog, а не показ
повідомлення на телефоні.

API, collector і notifier працюють з image ID `f52aad81…`; watchdog —
`978ec2d9…`. Локальний тег `avelren-app:latest` указує на образ watchdog,
а не на образ перших трьох сервісів. Через це звичайний recreate може
активувати інший код навіть без git pull. Перед deployment потрібні
незмінний image digest, перелік змін і план відкату.

На сервері змінені watchdog.py та telemetry-snapshot.sh, також є три
старі .bak/pre-88 файли. Встановлений snapshot, його checkout-копія й
кандидат збігаються (`577aa6c1…`). Встановлений backup і checkout збігаються
(`de881a23…`); ця сама копія є source-only в PR #1. Видаляти старі файли
або вирівнювати серверний checkout у межах аудиту не потрібно.

Вісім перевірених основних Python-залежностей у runtime збігаються з
requirements.lock нового репозиторію; runtime Python 3.14.7. Це перевірка
версій цих пакетів, не повний vulnerability-аудит усіх транзитивних залежностей.
Постійний Device ID collector збігається між runtime та ефективною
конфігурацією checkout; його значення не зберігали у звіті.

PR #1 окремо містить maintenance.py та `/status`, яких немає у PR #3 і
production (там 404). Це задокументована майбутня функція, не непомітна
частина перенесення Admin. Не включати її в розгортання PR #3 випадково.

## Схема, права та результат тестів Admin

На production лише 001–009; SHA всіх дев'яти відповідають кандидату.
Фізичний контракт застосованих міграцій перевірено read-only: проблем немає.
Власник перевірених application-таблиць, view та sequence — avelren_migrator.
Pin указує на `/var/lib/avelren-migrate-pin-009`, migrate має окремий profile.
Він лишається активним.

**Важлива знахідка:** усі чотири runtime-сервіси фактично підключені як
`avelren`, superuser. Наявність обмежених сервісних ролей та їхніх ACL
не означає, що сервіси вже ними користуються. Незавершений least-privilege
перехід потрібно завершувати окремою перевіреною процедурою, не зняттям pin.

У [тесті production_009](../services/backend/tests/database/api/test_production_009.py)
відтворені схема 009, виміряні ефективні ACL API/backup, один синтетичний
Admin та окрема синтетична legacy-superuser роль. Виміряні метадані лежать
у [фікстурі](../services/backend/tests/database/fixtures/production_009_admin_acl.json).
Реальні пристрої, токени, паролі, дамп production або його DSN не використані.

Доведені сценарії:

1. На 009 і legacy-, і обмежений API запускаються; workload та чинна
   Admin-телеметрія працюють; GET/POST `/admin/access` повертають unavailable.
   Журнал міграцій і чинний Admin збережені.
2. На копії такої схеми застосовані 010→011 від migrator; записи 001–009,
   їх SHA та applied_at збережені; повторний migrate ідемпотентний.
3. Після штатного admin_approve синтетичний PIN перевіряється через API:
   хибна спроба записується, правильна активує лише схвалений пристрій,
   попередній Admin утрачає доступ. API не може прямо змінити approval,
   PIN hash чи devices.is_admin; backup читає нову таблицю, запис заборонений.

## Що не переносити механічно і що ще бракує

| Пріоритет | Знахідка | Конкретний наступний результат |
| --- | --- | --- |
| Блокер переходу | Немає повного production Dockerfile/Compose/Caddy/systemd комплекту; latest і runtime відрізняються | Зібрати відтворюваний staging-комплект, перевірити mounts/DSN/entrypoints та незмінні image digests |
| Блокер переходу | Restore engine, orchestration, smoke-модулі й restore-тести ще не перенесені; останній відомий rehearsal — 17.08 | Перенести узгоджений restore-комплект і виконати відновлення в окремому тестовому середовищі з Timescale pre/post hooks |
| Блокер переходу | Runtime працює під superuser, схема pinned 009 | Підготувати окремий adoption/ACL-план та перевірити всі runtime-шляхи під сервісними ролями; не копіювати legacy DSN |
| До відповідного релізу | 90-day retention відсутній у перевірених опублікованих гілках, але Android-текст його обіцяє; старих пристроїв зараз 0 | Узгодити реалізацію й текст. Незакомічену 012 або альтернативні 011 не вважати прийнятими |
| Окрема кодова помилка | forecast.py:226 перетворює MAE=0 на null через truthiness-перевірку; файл побайтово успадкований | Малий окремий fix із тестом нульової MAE; не позначати старий код правильним лише через збіг SHA |
| Перед rollout нової функції | release_notice.py ще не перенесений; автоматичне maintenance-вікно перед reboot не доведене | Окремий перенос/перевірка, без обіцянок готовності на телефоні |
| Hardening | `/docs`, `/redoc`, `/openapi.json` публічні; немає трьох перевірених security headers; rootfs writable, pids_limit/cap_drop/no-new-privileges не задані | Визначити політику й перевірити в staging; не застосовувати неперевірені зміни на сервері |

Перенесені тести не замінюють усі старі integration-контракти: особливо
adoption, restore, ізоляцію секретів Compose та повний lifecycle сповіщень.
У CSV ці файли залишені видимими. Старі default paths `/opt/avelren`,
`/root/.config/rclone/rclone.conf`, старі схеми та миттєві watchdog push
не слід приймати за актуальні вимоги нового репозиторію.
