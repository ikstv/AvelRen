# Плановий перезапуск із правдивою плашкою

Ці сценарії — **source-only** перенесення механізму з гілки
`codex/automated-maintenance-window` старого `ikstv/AvelRen`. Вони не є
інструкцією чи дозволом розгортати щось на production.

`ops/maintenance-window.sh` атомарно публікує коротке вікно в
`/var/lib/avelren-telemetry/maintenance.json`, зчитує його через публічний
`/api/status` і лише після перевірки тих самих UTC-моментів `starts_at`,
`restarts_at` та `ends_at` чекає
перед операцією. Якщо API не підтвердив плашку, файл прибирається і сценарій
завершується помилкою: плановий outage не починається.

Типове вікно триває 600 секунд: `restarts_at` враховує 15-секундний бюджет
перевірки API й лишає щонайменше 75 секунд після її завершення, а після
планового моменту reboot — щонайменше 120 секунд захисного запасу. У файл також
записується поточний Linux `boot_id`. Після нового завантаження API бачить
інший `boot_id` і завершує плашку одразу, не чекаючи спливу всього вікна.

`ops/maintenance-reboot.sh` є обгорткою: він викликає publisher, а потім
передає керування `systemctl reboot`. Це гарантує, що ручний перезапуск не
відбувається до перевіреного оголошення. Прямий `systemctl reboot` цей
контракт обходить і для планових робіт не допускається.
Єдиний неблокуючий `flock` утримується від початку публікації до передачі
команди reboot. Паралельний другий запуск відмовляє до зміни файла й не може
стерти або підмінити сигнал першого.

Systemd shutdown-hook не підтримується: він стартує вже всередині процедури
вимкнення, де мережа та API не є надійною передумовою. Автоматизація тут
означає одну команду `avelren-maintenance-reboot`, яка сама виконує весь
ланцюжок; окремо створювати плашку оператору не потрібно.
Якщо перевірка перевищила часовий бюджет, очікування перервали, boot ID
недоступний API або команда `systemctl reboot` відмовила, сценарій
завершується без reboot і прибирає сигнал, щоб застосунок не показував
неправдивий стан.

Окремо погоджений production deployment 27.09.2026 підтвердив read-only mount
`/telemetry`, встановив перевірені скрипти поза checkout і точково оновив
API-модуль. Наступний окремо погоджений контрольний перезапуск підтвердив на
телефоні повну послідовність: технічні роботи → перезапуск сервера → сервер
онлайн. Детальний production evidence зафіксовано в `PRODUCTION-AUDIT.md`.

Локальний, ізольований контрактний тест:

```bash
bash ops/maintenance-window-contract-test.sh
```

Він підміняє `id`, `curl` та `sleep`, не звертається до production і не
перезапускає машину.
