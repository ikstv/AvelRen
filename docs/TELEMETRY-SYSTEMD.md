# Host telemetry systemd units

## Перенесені артефакти

`ops/avelren-telemetry.service` запускає встановлену копію
`ops/telemetry-snapshot.sh` як одноразову службу. `ops/avelren-telemetry.timer`
запускає її через 30 секунд після старту системи, а далі — раз на хвилину.
Знімок публікується у `/var/lib/avelren-telemetry/host.json`; API читає його
через read-only mount.

Під час перенесення адаптовано посилання `Documentation=` з історичного
`/opt/avelren/deploy/` на монорепозиторний `/opt/avelren/ops/`; пояснювальні
коментарі також приведено до нових шляхів. `ExecStart` і системні обмеження
збережено. Права запису служби обмежені каталогом snapshot; читання `/proc` і
`/run` лишається read-only. Мережеві сімейства потрібні для TLS-перевірки
сертифіката.

## Межа операцій

Цей документ описує перенесені файли й очікувані точки перевірки, але не є
дозволом на встановлення, перезапуск, `daemon-reload`, увімкнення timer або
будь-яку іншу дію на production. **Розгортання можливе лише після окремої
великої команди власника та його явного дозволу на конкретні кроки.**

У CI `systemd-analyze verify` перевіряє unit-файли на ізольованому runner.
Workflow встановлює їх у тимчасове середовище, потрібне для перевірки абсолютних
шляхів; він не виконує `daemon-reload` і не запускає чи не вмикає units.

Історична процедура в `AvelRen-ops/deploy/telemetry-isolation-deploy.md` містить
команди `git pull`, `docker compose build migrate`, примусове пересоздання API
та rollback. Її не можна копіювати чи виконувати механічно: міграційний pin,
Compose-профіль і теперішній код відрізняються. Перед майбутньою операцією
потрібно підготувати актуальний план, перевірки й відкат для конкретного стану.

Коли таку операцію буде окремо дозволено, фактичними точками приймання мають
бути: правильні встановлені файли й їхні хеші, активний timer із наступним
запуском, успішний oneshot, валідний свіжий JSON та його read-only доступність
у API-контейнері. У цьому етапі жодна з цих серверних змін не виконувалась.
