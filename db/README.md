# База даних: ізольований етап перенесення

Міграції `001`–`011` і `security/bootstrap.sql` перенесено без змін із
коміту `4a8e010aeb02d2d77fef3fc1297e67f4f5e5ab27`. Походження кожного
файла та SHA-256 наведені в [DB-PROVENANCE.json](../docs/DB-PROVENANCE.json).
Той самий маніфест містить migrate.py і штатний postgres-bootstrap.sh.

На production під час останньої звірки записані лише `001`–`009`.
Наявність тут `010` (права) й `011_admin_access` не означає їх застосування
на сервері. Альтернативні міграції 011 зі старих гілок не перенесені.
Цей набір є кандидатом для тестового середовища; процедура переходу
чинного сервера, adoption і migration pin залишаються окремою задачею.

## Запуск перевірки

На Linux із Docker Compose, з кореня репозиторію:

```sh
bash scripts/test_database.sh
```

Сценарій створює окремий проєкт `avelren-db-test-*`, порожню TimescaleDB
у tmpfs, тестові ролі та мережу `internal: true`. Порти на хост не
публікуються, production volumes та `.env` не використовуються.
Після завершення або помилки тестові контейнери й мережа видаляються.
GitHub запускає цей самий сценарій у workflow `database.yml`.

Перевірки охоплюють:

- створення нової БД штатним bootstrap та міграції від migrator-ролі;
- збереження SHA-256 і часу застосування при повторному запуску;
- перехід синтетичної схеми 009 до 011 зі збереженням її журналу;
- відмову при зміненому файлі, прогалині або невідомій версії в журналі,
  відсутній історії чи пошкодженій фізичній схемі;
- права collector/notifier/watchdog/API, відсутність superuser у сервісів;
- читання backup-роллю всіх публічних таблиць і послідовностей,
  заборону запису та справжній pg_dump під цією роллю;
- два однакові вимірювання в різні хвилини, запис помилки джерела,
  створення алерта та його обробку notifier під відповідними ролями.

HTTP і FCM підмінені, виходу до єЧерги немає. Для пошкоджень схеми кожен
тест створює нову БД із синтетичною назвою й гарантовано видаляє її.
Запуск pytest без точного тестового DSN і маркера заборонено до SQL.

Це не тест відновлення реальної резервної копії, не production adoption
і не перевірка Admin API. Ці етапи ще попереду. Локально на Windows Docker
недоступний: там перевіряються Python-код, походження файлів і відмова
небезпечного запуску; повний SQL-сценарій виконує GitHub Actions.
