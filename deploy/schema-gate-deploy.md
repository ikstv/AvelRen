# Деплой: стартовий гейт схеми (#88)

> **Це перший деплой застосунку, задокументований у проєкті.** Процедури не
> існувало: у `deploy/` був лише adoption-рунбук і `telemetry-isolation-deploy.md`
> про одну конкретну зміну. Цей документ виведено з того шаблону, з поправками на
> те, що змінилося після Gate 11 3B.2.
>
> **Мерж не активує гейт. Активує цей деплой.** До нього прод виконує старий код,
> і жодна з перевірок #88 на бойовій системі не працює.

---

## 0. Що це робить і чим ризикує

**Робить:** перезбирає `avelren-app:latest` з нового коміта і перезапускає
чотири сервіси, які відтоді при старті звіряють версію схеми.

**Ризик, і він повний:** гейт fail-closed і живе в **кожному** з чотирьох
сервісів. Хибний гейт означає не деградацію однієї функції, а **відмову старту
всього рантайму**. Тому відкат вирішується **до** збірки, а не після падіння.

**Дельта коду мінімальна.** Виміряно 2026-08-17: останній коміт, що чіпає вміст
образу (`app/src`, `app/pyproject.toml`, `app/Dockerfile`) — `9400a8d` від
08-15, тобто **раніше** за збірку поточного образу (08-16 07:26Z). Отже цей
деплой додає до запущеного коду рівно одну зміну — сам гейт.

---

## 1. Передумови — доступ

- `root`/sudo на бойовому хості; `docker` під `sudo`;
- `/opt/avelren` — чекаут на `main`, **чисте дерево**;
- на хості **немає** окремого deploy-скрипта (виміряно: у `/usr/local/sbin/`
  лише `avelren-backup`, `avelren-restore`, `avelren-telemetry-snapshot`).
  Деплой ручний — цей документ і є процедура.

---

## 2. Головна пастка: `-f docker-compose.yml`

На хості лежить `docker-compose.override.yml` — **root-owned, поза git**
(`.gitignore`), артефакт інциденту 2026-08-14. Він робить дві речі:

1. форсує `DATABASE_URL` (легасі суперюзер) для `collector`, `notifier`,
   `watchdog`, `api` — саме тому рантайм досі на легасі-конекті, хоча володіння
   вже на семи ролях;
2. монтує `migrate` каталог `/var/lib/avelren-migrate-pin-009` як `/migrations`
   (ro) — це пін `001–009`, поставлений після 3B.2.

**Іменування compose-файлу вимикає автопошук**, а разом із ним — і override.
Наслідок подвійний і тихий: `migrate` побачить репозиторний `010` і **заштампує
його поза 3D**, а чотири сервіси спробують per-role DSN, на які прод ще не
перемкнено, і **не піднімуться**.

Тому в усіх командах нижче **`-f` не вживається взагалі** — покладаємось на
дефолтний авто-load `base + override`. `--no-deps` — другий пояс, не перший.

## 3. Базлайн — зняти й записати

```bash
cd /opt/avelren
git rev-parse HEAD; git status --porcelain
sudo docker ps --format '{{.Names}}\t{{.CreatedAt}}\t{{.Status}}'
sudo docker image inspect avelren-app:latest --format '{{.Id}} {{.Created}}'
curl -fsS https://api.bordersignal.pp.ua/api/health
sudo docker compose exec -T db psql -U avelren -d avelren -At \
  -c 'SELECT max(version) FROM schema_migrations'
```

Останній рядок має дати `009_observability`. Це число знадобиться у прийманні:
воно **мусить лишитись тим самим** після деплою.

### 3.1 Довести, що override активний — до збірки

Уся процедура стоїть на тому, що дефолтний авто-load підхоплює
`docker-compose.override.yml`. Але він machine-local і поза git — тобто зникає
**тихо**, і жоден із запобіжників розділу 2 цього не ловить: `--no-deps` не
поверне пін, а відсутність `-f` не поверне легасі-DSN, якщо повертати нема чого.

```bash
( set -o pipefail
  sudo docker compose config | grep -E 'avelren-migrate-pin-009|DATABASE_URL' \
    | sed -E 's#(postgresql://[^:]+):[^@]*@#\1:***@#g'
) || echo "STOP: override не активний або compose-модель невалідна"
```

Порожньо → **стоп до збірки**. Це ловить зниклий override у найдешевшій точці —
замість того, щоб дізнатись про це через restart-loop чотирьох сервісів або,
гірше, через тихий штамп `010`.

## 4. Відкат — вирішується ЗАРАЗ, до збірки

Шаблон `telemetry-isolation-deploy.md` відкочується перезбиранням зі старого
коміта. Під тиском це хвилини, яких немає, і воно рухає чекаут. Замість цього —
зберегти образ:

```bash
sudo docker tag avelren-app:latest avelren-app:pre-88
sudo docker image inspect avelren-app:pre-88 --format '{{.Id}}'   # = Id із базлайну
```

Відкат тоді — секунди, без перезбирання:

```bash
sudo docker tag avelren-app:pre-88 avelren-app:latest
sudo docker compose up -d --force-recreate --no-deps api collector notifier watchdog
git checkout 86d3534        # чекаут теж назад; повернення на main — явним кроком
```

**Не пропускати `git checkout` при відкаті.** Інакше чекаут лишиться попереду
образу — рівно та розбіжність, яку ми сьогодні розбирали й яка робить
`PROD_PIN` брехливим.

## 5. Деплой

```bash
cd /opt/avelren
git pull                      # main -> новий head
git rev-parse HEAD            # записати: це майбутній PROD_PIN
git status --porcelain        # МУСИТЬ бути порожньо

export SOURCE_COMMIT=$(git rev-parse HEAD)
sudo -E docker compose build migrate     # той самий образ avelren-app:latest
```

> **`sudo -E` обов'язковий.** Без нього sudo вирізає env, `SOURCE_COMMIT` не
> долітає, і `AVELREN_GIT_SHA` лишається порожнім — саме те, що ми виміряли на
> поточному образі (порожній і в env, і в шарах: провенанс невідновний).

**Перевірити провенанс ДО перезапуску** — це найдешевша точка відмови:

```bash
sudo docker image inspect avelren-app:latest \
  --format '{{range .Config.Env}}{{println .}}{{end}}' | grep AVELREN_GIT_SHA
```

Має показати повний SHA нового коміта. Порожньо — **стоп**, `-E` не спрацював;
перезапускати ще нема сенсу.

Тоді — чотири сервіси:

```bash
sudo docker compose up -d --force-recreate --no-deps api collector notifier watchdog
```

`caddy` не чіпаємо: нашого коду в ньому немає.

## 6. Приймання — п'ять перевірок, усі обов'язкові

```bash
# 1. жоден сервіс не в restart-loop
sudo docker compose ps

# 2а. гейт виконався у трьох, що самі налаштовують логування
for s in collector notifier watchdog; do
  echo "== $s"; sudo docker compose logs --no-color --tail 50 "$s" | grep -i 'схема узгоджена'
done

# 2б. api — доказ інший, і він сильніший за рядок у лозі (див. нижче)
curl -fsS https://api.bordersignal.pp.ua/api/health >/dev/null && echo "api обслуговує => гейт пройдено"

# 3. HTTPS живий
curl -fsS https://api.bordersignal.pp.ua/api/health

# 4. 010 НЕ заштамповано — доказ, що migrate не запускався
sudo docker compose exec -T db psql -U avelren -d avelren -At \
  -c 'SELECT max(version) FROM schema_migrations'      # має бути 009_observability

# 5. збирач пише далі
sudo docker compose exec -T db psql -U avelren -d avelren -At \
  -c "SELECT max(time) FROM collector_runs"
```

Перевірка 2 — головна: саме вона відрізняє «сервіс піднявся» від «гейт
відпрацював». Відсутність рядка в `collector`/`notifier`/`watchdog` означає, що
сервіс стартував зі старого образу — тобто той самий тихий розрив, від якого
гейт і придуманий.

> **Чому в `api` шукати рядок не можна — і не треба.** `api.py` не викликає
> `logging.basicConfig`: логування там налаштовує uvicorn, а він конфігурує лише
> власні логери й лишає root без хендлера на INFO. Тобто `log.info` гейта в
> логах `api` не з'явиться **навіть коли гейт відпрацював** — і пошук рядка дав
> би хибний «стоп» на справному сервісі.
>
> Натомість для `api` є сильніший доказ: гейт викликається в `lifespan` **до**
> `yield`. Якщо він підніме виняток, startup провалиться і uvicorn вийде —
> контейнер піде в restart-loop і його спіймає перевірка 1. Отже **факт, що
> `/api/health` віддає 200, сам по собі означає, що гейт пройдено**. Це не
> послаблення перевірки, а перехід від свідчення (лог) до наслідку (сервіс
> обслуговує).

Перевірка 4 — доказ, що `--no-deps` спрацював і `migrate` не втягнувся.

## 7. Стоп-правила

Відкат (розділ 4) негайно, якщо:

- бодай один із чотирьох у `Restarting` довше за одну спробу;
- `/api/health` не відповідає понад 2 хв після старту;
- `max(version)` став `010_*` — `migrate` таки запустився, і це вже не тільки
  про деплой;
- у логах гейта `SchemaTooOldError` — гейт вважає схему замалою, і поки
  причина невідома, рантайм важливіший за перевірку.

`docker compose down`, `restart` без `--no-deps`, і будь-який голий `up -d` —
**не робити** ні в якому разі, включно з панікою.

## 9. Що цей деплой змінює для Gate 11

Він рухає чекаут, а отже й `PROD_PIN`, а отже переприв'язує трійку
`evidence ↔ repo ↔ runner`. Evidence 3B.2 (`evidence-3b2-86d3534-…`) після цього
лишається дійсною лише як історичний запис: будь-яка майбутня adoption
вимагатиме evidence на новому коміті.

**Рішення: цей деплой робиться ОКРЕМО від 3C re-prep, і не чекає на неї.**

Спокуса звести їх в одне вікно є, і аргумент за неї очевидний — пін рухається
раз замість двох. Аргумент слабкий, і його свідомо відхилено:

- рух піна коштує один рядок і одну PR — це не та економія, заради якої варто щось поєднувати;
- об'єднання зчіплює **оборотну** зміну (образ; відкат тегом за секунди) з **необоротною** (cutover DSN із мутацією каталогу), тобто імпортує ризик другої в першу;
- економії на evidence немає навіть теоретично: 3C однаково потребуватиме свіжого evidence на тодішньому коміті, коли б вона не сталася;
- 3C — проєктна робота на тижні (продового режиму cutover не існує, з шести гейтів реалізований один, `collector_freshness` потребує перепроєктування). Чекати на неї означає лишити гейт без діла, а пін `001–009` — тимчасовий протез — зробити постійним.

Досвід 3B.2 говорить те саме: вона вдалася тому, що робила одну річ.
